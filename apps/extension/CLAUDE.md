# apps/extension — subsystem notes

Loaded when working under `apps/extension`, the Trakwyn Clipper. Paths below are relative to `apps/extension/`.

## Build (WXT, JEF-386)

One source, one MV3 manifest per browser, from `wxt.config.ts`. Entrypoints are in `src/entrypoints/` (`popup/`, `background.ts`, `content.ts`); shared code is in `src/lib/`. Content-script `matches` live in `content.ts`'s `defineContentScript`, not the config.

```bash
pnpm dev             # build + watch Chrome into .output/chrome-mv3-dev (no browser launch); dev server on :3002
pnpm build           # Chrome  -> .output/chrome-mv3
pnpm build:safari    # Safari  -> .output/safari-mv3
pnpm package:safari  # build:safari, then (re)generate the Xcode project in safari/
pnpm build:firefox   # Firefox -> .output/firefox-mv3
pnpm zip:firefox     # add-on zip + AMO sources zip in .output/
```

- Load Chrome from `.output/chrome-mv3` (chrome://extensions → Load unpacked).
- **Firefox (JEF-423):** load `.output/firefox-mv3` from `about:debugging` → This Firefox → Load Temporary Add-on (pick its `manifest.json`). See "Firefox" below for how it differs and how it is released.
- **Safari:** open `safari/Trakwyn Clipper/Trakwyn Clipper.xcodeproj`, run the "Trakwyn Clipper" scheme, then in Safari enable Develop → Allow Unsigned Extensions and turn the Clipper on in Settings → Extensions. The project references `.output/safari-mv3` in place, so after the first `package:safari` a `build:safari` plus an Xcode rebuild picks up changes. Re-run `package:safari` only to regenerate the project (e.g. a new permission). The bundle ID `com.trakwyn.clipper` is a placeholder until the App Store release.
- **Version (JEF-389):** `package.json` holds it and release-please bumps it; `wxt.config.ts` sets none, so WXT writes that number into both manifests. Releasing is merging the Clipper's release PR (root `CLAUDE.md`), then building and uploading by hand: see "Releasing the Clipper" below. The Xcode project's `MARKETING_VERSION` is a committed copy that `package:safari` rewrites from `package.json`. A release PR does not touch it, so run `package:safari` after merging one and before a Safari build.
- **API URL (JEF-412, JEF-419):** `DEFAULT_API_URL` is `API_URLS.DEVELOPMENT` (localhost) only under `pnpm dev`, and `VITE_API_URL` at build time everywhere else (`.env.example`). The production URL is not in the source: the release workflow reads it from the `CLIPPER_API_URL` repository variable, and a `build` or `zip` without `VITE_API_URL` fails in a `build:before` hook in `wxt.config.ts` (`.env` counts). The check is a hook, not a throw in `resolveDefaultApiUrl`, because `wxt prepare` (postinstall, typecheck) imports that with no variable set and must keep working; the resolver returns an empty URL there. CI writes a placeholder `apps/extension/.env` before `pnpm build`, since nothing in CI calls the API. After `pnpm setup:worktree`, set `VITE_API_URL` in `apps/extension/.env` (the copied `.env.example` leaves it blank) before building. `apiUrls.ts` is separate from `constants.ts` because `wxt.config.ts` imports it in Node, where `import.meta.env` is undefined. **Web URL (JEF-428):** the popup's links to the web app (a saved application, `/settings/ai`) use `DEFAULT_WEB_URL`, which is `WEB_URLS.DEVELOPMENT` under `pnpm dev` and `VITE_WEB_URL` at build time (the release workflow's `CLIPPER_WEB_URL` repository variable, the web origin such as `https://www.trakwyn.com`). It is never derived from the API URL: production serves them from different hosts (`api.trakwyn.com` vs `www.trakwyn.com`), and deriving it sent "Open application" to the API. A `build` without it fails in the same `build:before` hook, and CI's placeholder `.env` sets both. There is no options page and no user-set URL (JEF-418): the first store version has no settings screen, so the extension talks only to the API it was built for.
- **Manifest (JEF-412):** `src/manifest.ts` builds it for both browsers (`manifest.test.ts`). **A production build has no `host_permissions`:** only `pnpm dev` adds the local API. This is deliberate, because a host permission added in an update disables the extension until every user re-approves it, so the first store version has to be right.
  - The API needs none: `corsPlugin.ts` lets any `chrome-extension://`, `safari-web-extension://` or `moz-extension://` origin through and sets no header allow-list, and the Clipper sends bearer tokens, not cookies. If a proxy ever strips those CORS headers, add `optional_host_permissions` for it; an _optional_ permission can be added in any update without re-prompting.
  - The job boards are covered by the content script's `matches` in `entrypoints/content.ts` (the real list), and the popup reads the tab through `activeTab`. Do not repeat them as `host_permissions`. A new board is a new `matches` entry, and the same re-approval warning applies to it.
- Use `browser` from `wxt/browser`, never `chrome.*`. Message listeners return a promise rather than calling `sendResponse` and returning `true`, which Safari does not honour reliably.

## Auth

Both tokens come from the API's `*Mobile` mutations and live in `browser.storage.session` (`lib/storage.ts`). The background worker owns refresh, since the API rotates refresh tokens (`RUNTIME_MESSAGES`).

**Keep me signed in (JEF-421).** The sign-in screen has an unticked-by-default box. Ticked, `setAuth(auth, true)` also writes the **refresh token only** to `browser.storage.local` (`STORAGE_KEYS.PERSISTED_REFRESH_TOKEN`); the access token and `expiresAt` never leave `storage.session`. The key's presence is the choice, so nothing else records it.

- **Restore:** a browser restart empties `storage.session` but not `storage.local`. `refreshToken()` falls back to the persisted token when there is no session, so the background's startup `scheduleRefresh`, the popup's `init` and `authedGql` all restore through the same single-flighted refresh.
- **Rotation:** every refresh stores the new pair with the same `persist` flag, so the persisted copy is always the current token. The API treats a superseded token as reuse and revokes the session (`RotateRefreshTokenUseCase`), so a stale copy must never be left behind.
- **Clearing:** sign-out (`clearAuth`) and a refresh the API refuses remove both copies. An **unreachable** API (the browser started offline) clears only the session (`clearSessionAuth`) and keeps the persisted token for the next try. A later sign-in without the box removes an older persisted token.
- **Content scripts can read `storage.local`** (only `storage.session` is closed to them by default) and `content.ts` runs inside job-board pages, so `restrictLocalStorageToTrustedContexts` limits it to `TRUSTED_CONTEXTS` before every persisting write. It is applied per browser session, so it is called on each write rather than once. A browser without `setAccessLevel` is left as is. Never widen `storage.session`'s access level either.
- **Safari tab sign-in** keeps the choice in the pending login (`PendingTabOAuth.keepSignedIn`), so a background restarted mid-login still honours it.
- **The token is on disk unencrypted** in the browser profile, so the API's absolute session lifetime (`SESSION.ABSOLUTE_TTL_MS`, JEF-422) is what bounds a copied one. Keep the box opt-in.

**Google/GitHub sign-in** runs in the background (the popup closes when the sign-in opens) and is chosen by feature detection in `lib/api.ts`:

- **Chrome** (`identity` present, JEF-383): `launchWebAuthFlow` to `…/start?platform=extension&extensionId=…`, handed back on `https://<id>.chromiumapp.org/`. The ID must be in the API's `EXTENSION_OAUTH_IDS`. A Web Store build has its own permanent ID (the unpacked ID differs, since Chrome derives it from the folder), so create the draft listing first, take the ID from the dashboard and add it to the production `EXTENSION_OAUTH_IDS` (`infra/gcp`) before the listing goes live, or Chrome sign-in fails for every user.
  - **The Web Store ID is `pnpgngnojencbggokjhpfhmliijakmhe`** (JEF-415), owned by an individual developer account's publisher, not a group publisher. It is permanent for the listing. It goes in production `EXTENSION_OAUTH_IDS`; the dashboard URL is `…/devconsole/<publisher>/pnpgngnojencbggokjhpfhmliijakmhe/edit`.
- **Safari** (no `identity` API, JEF-386): `lib/tabOAuth.ts` opens `…/start?platform=extension-tab` in a tab and watches it until it lands on the API's `/auth/oauth/extension/done`, then closes it. Safari may unload the background mid-login, so the login (tab ID, PKCE verifier and "Keep me signed in" choice) is also in `storage.session`, and `registerTabOAuthListeners` is registered when the background starts so a restarted one can still finish it. This is why the Safari manifest has `tabs`.

Either way, the handoff code is redeemed with `exchangeMobileOAuthCode` and this login's PKCE verifier.

## Error reporting (JEF-387)

The Clipper reports faults to the same PostHog project as web and mobile, through `lib/observability/`. These points are load-bearing:

- **Off by default.** Without `VITE_POSTHOG_KEY` at build time (`.env.example`) no request is made, which is the intended state in dev and CI. The key is the public `phc_` one, inlined into the bundle like web's.
- **No SDK.** `report.ts` posts to PostHog's capture endpoint with `fetch`, as web's Vercel function does. `posthog-js` needs a `window` and `localStorage`, which the background service worker has neither of. PostHog answers the CORS preflight for extension origins, so the manifest has no PostHog host permission; adding one would prompt every user on update.
- **No person, no consent gate.** Reports are operational data, not analytics: `$process_person_profile: false`, a random `distinct_id` per event, `$geoip_disable`, and nothing stored between reports. Only faults are sent. A product event (a clip saved, a sign-in) would need a consent decision first. The reasoning is in `infra/posthog/README.md` ("Browser extension errors").
- **Two contexts report: `background` and `popup`.** Each entrypoint calls `initObservability` first, which adds the `error` and `unhandledrejection` listeners; the popup also sits in `ErrorBoundary`. The content script never reports and has no listeners: on LinkedIn's page they would catch LinkedIn's errors.
- **What is sent.** `$exception` for bugs; `graphql_request_failed` for an unreachable API or a 5xx (never a 4xx or a domain code, the same rule as web and mobile); `token_refresh_failed` and `oauth_login_failed` with a `reason`; `parser_result` when a job's page on a known board gave the parsers less than a clip needs (on LinkedIn and Indeed, only when the URL names a job, so a search page is not a fault). `ApiError` is the API answering, so it is shown to the user and not reported. An error `gql` reported is marked (`markReported`), so no caller reports it again.
- **What is never sent.** Tokens, the email, the OAuth handoff code, the PKCE verifier, GraphQL variables, job content, or a page URL. `parser_result` names the board (`JOB_BOARDS` in `constants.ts`), not the hostname, because a Workday or Greenhouse hostname carries the employer's name. Everything passes `scrub.ts`, a copy of web's that `scrubParity.test.ts` holds identical.
- **`traceparent` goes to the API only**, on every `gql` request. The same id is the `trace_id` on that request's failure event and on the next exception, which links a PostHog report to its Axiom trace.
- **A report never throws or retries.** A failed send is dropped.

## Reading a posting: built-in or AI (JEF-420)

The popup shows two buttons on a job page (`ReadButtons`): **Read with parser** and **Read with AI**. The user chooses per clip; there is no stored setting for it. The popup opens on the built-in result.

- **Parser** is the content script's parsers (`GET_JOB_DATA`). **AI** adds `GET_PAGE_TEXT` (`lib/parsers/pageText.ts`: the main area's text, else the body, capped at `PAGE_TEXT_MAX_CHARS`, the API's `JOB_POSTING_MAX_CHARS`), then the existing `parseJobDescription(text)` mutation (`lib/api.ts`, via `lib/aiRead.ts`). No API change, and no new permission: it works only on the boards the content script matches.
- **"Read with AI" is disabled without a default AI key.** `getPopupBootstrap` (`lib/api.ts`) asks `me { … defaultLlmProvider }` and `llmApiKeys { provider }` in the popup's one startup request (JEF-457), and `aiAvailable` is true only when the default provider has a saved key (a default whose key was deleted would fail with `AI_NOT_CONFIGURED` only after the page text was sent). The disabled button links to the web app's `/settings/ai`. A missing key list reads as "no key"; the parser still works. Until the request answers, the button is disabled with `aria-busy` and no link.
- **Merge rule** (`lib/parsers/mergeAiResult.ts`): the user asked for the AI, so its answer replaces the parser's for every field it gave; a null or blank AI field never overwrites a parsed one. It merges into the parser's result (`Clip.builtin`), not into an earlier AI read. A clip the AI changed is editable in `ClipCard` before saving, since AI output is a suggestion. **Read with parser** drops the AI result and reads the page again.
- **Failure is never a dead end.** `AI_NOT_CONFIGURED`, `AI_LIMIT_REACHED`, `AI_PROVIDER_ERROR`, `AI_RESPONSE_INVALID` and `RATE_LIMITED` get their own copy (`AI_ERROR_MESSAGES`); the popup keeps the clip and shows a dismissible notice.
- **Privacy.** Only pressing **Read with AI** sends the page's text, to the user's own LLM provider through Trakwyn's API. Page text and the result are never reported to PostHog; `parser_result` is unchanged.

## Popup startup (JEF-457)

The popup shows the clip from the content script's parsers as soon as it has it, without waiting for the network. The account fills in afterwards.

- **One request.** `getPopupBootstrap` (`lib/api.ts`, operation `PopupBootstrap`) returns the user and `aiAvailable`. Do not add a second startup query: put a field in this one.
- **Order in `App.tsx`.** `init` reads storage, then starts the refresh through the background only when the access token is near expiry or a "Keep me signed in" token can restore the session. `loadReadyScreen` renders the clip and the cached user, then waits for the refresh and the bootstrap. A refused refresh goes to sign-in without `logout`, so an offline browser keeps its persisted token. A 401 calls `logout`.
- **Cached user.** The last confirmed `CurrentUser` is kept in `storage.session` (`STORAGE_KEYS.CACHED_USER`), which content scripts cannot read. `clearSessionAuth` and `clearAuth` remove it with the session. It is only shown: **Save stays disabled until the API confirms the user** (`Account.confirmed`), and "Read with AI" until it answers.
- **A load can be superseded.** Signing out, or a new load, bumps `loadId`, so a late answer to an old load is dropped. Read results go through `updateClip`, which ignores them once the popup has left the ready screen.
- **Timings.** `lib/startupTiming.ts` records `popup:<stage>` `performance` measures (`storage`, `refresh`, `readActiveTab`, `bootstrap`, plus `clip-shown` and `account-confirmed` measured from popup open). Read them in the popup's DevTools with `performance.getEntriesByType('measure')` on any build; `pnpm dev` also logs them. Nothing is sent.
- **The background's `scheduleRefresh` is a `setTimeout`**, so it stops when the MV3 worker is suspended, and after an idle spell the popup usually finds the access token expired and asks for a refresh. `alarms` would survive suspension but is a new permission (see "Releasing the Clipper").

## Releasing the Clipper (JEF-418)

Web Store ID `pnpgngnojencbggokjhpfhmliijakmhe`. A published version can never be rolled back, only replaced by a higher one, and review takes hours to days, so the first public release is staged and every later one follows the same steps. From JEF-419 the release workflow builds the zip and uploads it, and from JEF-429 it submits it for review too (below); a person still publishes it.

1. **Pick the version.** release-please proposes it from the commit types since the last `clipper-v…` tag (root `CLAUDE.md`). To force one, set `"release-as"` on `apps/extension` in `release-please-config.json`; the release PR then proposes exactly that, and **the entry must be removed in the next PR after the release is tagged**, or the next release is forced to the same number. A `Release-As:` footer is not reliable here: the one on #1017's squash commit was ignored (release-please went on proposing `0.3.0`). The first public release is **1.0.0**, forced this way (JEF-418). Never edit a version or `CHANGELOG.md` by hand.
2. **Merge the Clipper's release PR.** It bumps `package.json` and `CHANGELOG.md`, and the workflow tags `clipper-v<version>` and creates the GitHub Release. Check that the PR touches only those two files.
3. **CI builds, uploads and submits for review (JEF-419, JEF-429).** Merging the release PR starts the `clipper-store` job in `.github/workflows/release.yml`, only when release-please reports a Clipper release. It checks out the `clipper-v<version>` tag, builds with `VITE_POSTHOG_KEY` from the repository variable `CLIPPER_POSTHOG_KEY` (the public project key, `terraform -chdir=infra/posthog output -raw project_api_key`), `VITE_API_URL` from the repository variable `CLIPPER_API_URL` (the full production `/graphql` URL, so the URL lives in repository settings and not in the workflow) and `VITE_WEB_URL` from `CLIPPER_WEB_URL` (the web origin), and fails unless the bundle contains both URLs, the manifest's `version` equals the tag and it has no `host_permissions`. It then compares the manifest with the previous `clipper-v…` release's zip and fails if `permissions` or any content-script `matches` entry is new, since nobody looks at the package before it is submitted: release that one by hand (steps 4 and 5, uploading the zip yourself). Otherwise it attaches `trakwynextension-<version>-chrome.zip` to the GitHub Release and runs `wxt submit`, which uploads the package to the existing listing and submits it for review. It passes `--chrome-publish-type DEFAULT_PUBLISH`, so an approved version is published to everyone with no further step (step 5). If the job fails before the upload, nothing reached the store. If the cause is outside the workflow (a missing variable or secret), fix it and re-run the job from the Actions tab. If the cause is in the workflow file, a re-run does not help, since it uses the file from the commit it first ran on: land the fix on `main`, then run **Release** by hand (Actions → Release → Run workflow) with `clipper_tag` set to the existing tag, e.g. `clipper-v1.2.0`. That runs only the Chrome and Firefox store jobs for the tag, with the current file; release-please does not run, so nothing is tagged or versioned (JEF-454). If it fails at the upload, check the dashboard before re-running, since the store refuses a version it has already seen.
4. **Check the package** (the release asset, or `.output/trakwynextension-<version>-chrome.zip` after a local build). In its `manifest.json`: `key` is the listing's public key (`manifest.ts`), `permissions` are `storage`, `activeTab` and `identity`. The job already checks `version` and `host_permissions`, and refuses to submit when `permissions` or content-script `matches` grew since the previous release. If either grew, the store disables the extension for every user until they re-approve it: do not ship that by accident. The job only compares with the previous release, so review the whole list when you change it on purpose. The bundle's only `localhost` is the unused development default in `apiUrls.ts`.
5. **Review and publish.** The job has already submitted the package, and approval publishes it to every user at once: there is no staged rollout and no step for you (JEF-429). A version you submit by hand (when the job refused it, or a first release) is published as you choose in the dashboard's submit dialog. For the first release set the distribution to **Unlisted** or **Trusted testers**. If review asks about a permission, answer from `store/listing.md`; the data-use answers there must still match the privacy policy and what the build does (tokens, `storage`, what is sent), so change them together whenever the Clipper's storage or network use changes.
6. **Verify the published build from the store** once it is live, not an unpacked one: open the store link in a clean Chrome profile, install, then sign in with Google and with GitHub against production and clip a job from LinkedIn and from one other board. Check the extension's ID is the one above.
7. **Watch the health dashboard.** With nothing staged, the new `release` reaches everyone as browsers update, so watch the Clipper health dashboard (`infra/posthog/README.md`) for `graphql_request_failed`, `token_refresh_failed`, `oauth_login_failed` and `parser_result`. A bad version cannot be rolled back, only replaced: ship the fix as in "After launch" below. (The first public release was a by-hand, staged one.)
8. **Confirm** the published version is the tag's. Installed copies update on the browser's own schedule, so the old version stays in use for days: that is why the API keeps old clients working (`apps/api/CLAUDE.md`, "Client compatibility").

### Web Store credentials for the upload job

The job uses Chrome Web Store API v2, which authenticates as a Google Cloud service account, so there is no consent screen and no refresh token to renew. It reads four repository secrets: `CHROME_EXTENSION_ID` (the ID above), `CHROME_PUBLISHER_ID`, `CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL` and `CHROME_SERVICE_ACCOUNT_PRIVATE_KEY` (the key's PEM, multi-line).

To set up:

1. `terraform apply` in `infra/gcp` enables the **Chrome Web Store API** and creates the `chrome-web-store-publisher` service account (no project roles). Create its JSON key with `gcloud`, not Terraform, so it stays out of state (`infra/gcp/README.md`, "Rotate the Web Store key").
2. In the Web Store developer dashboard (signed in as the listing's owner), open **Account** and add the service account's email as a user. This is the one step that cannot be scripted, and without it every call is refused. Copy the **Publisher ID** from the same page.
3. Set the secrets: `gh secret set CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL`, and `gh secret set CHROME_SERVICE_ACCOUNT_PRIVATE_KEY < key.pem` with the JSON's `private_key` value written out as a PEM file (`jq -r .private_key key.json > key.pem`), then delete the JSON and the PEM.

`wxt submit --chrome-api-version v2 --dry-run` with the same variables in the environment checks the credentials without uploading. To rotate, create a new key, replace `CHROME_SERVICE_ACCOUNT_PRIVATE_KEY` and delete the old key in the Cloud console. Submitting for review and publishing on approval are both automatic (JEF-429). These are plain Actions secrets, not a GitHub App: only the store call needs them, and the job runs inside the release workflow, so the `GITHUB_TOKEN` limitation in `release.yml` does not apply.

Safari is a separate release through the App Store (`package:safari`, above) and is not covered here. Firefox is covered next.

## Firefox (JEF-423)

One source again: `pnpm build:firefox` and `pnpm zip:firefox` use the same entrypoints and the manifest from `src/manifest.ts` (`manifest.test.ts`). It differs from Chrome in four ways:

- **Sign-in is the tab flow, like Safari.** Firefox exposes `browser.identity` only when the manifest asks for the permission, so the Firefox manifest has `tabs` and not `identity`, and `supportsWebAuthFlow()` in `lib/api.ts` is false there with no browser check. Do not add `identity`: its `launchWebAuthFlow` redirects to `*.extensions.allizom.org`, which the API would not redirect to, and no extension ID would go in `EXTENSION_OAUTH_IDS`. The API needs only `moz-extension://` in `EXTENSION_ORIGIN_SCHEMES` (its host is a per-install UUID, so CORS matches the scheme).
- **Gecko settings.** `browser_specific_settings.gecko` carries the add-on ID `clipper@trakwyn.com` (`FIREFOX_ADDON_ID`; permanent once published), `strict_min_version` 140 (the first desktop Firefox that reads `data_collection_permissions`) and the data-collection declaration AMO requires of a new add-on. The declaration must match `store/firefox-listing.md`, `store/listing.md` and the privacy policy; change them together. There is no `key`, which is the Web Store's.
- **Background.** MV3 in Firefox is an event page (`background.scripts`), which WXT emits. Nothing in it may assume a service-worker global.
- **No `setAccessLevel`.** Firefox cannot restrict `storage.local` to trusted contexts (`restrictLocalStorageToTrustedContexts` leaves it as is), so on Firefox the "Keep me signed in" refresh token is readable from the content script's isolated world. It is not reachable by the page itself, and the box stays opt-in; do not run page-controlled code in the content script.

**Releasing to AMO (JEF-437, JEF-458).** Version and tag are the Chrome ones (steps 1 and 2 above). AMO has no draft or deferred publishing, and no staged rollout: a listed version goes to review, and one that passes goes live. Like the Web Store job since JEF-429, it runs with no manual step, so the checks below are the only ones before AMO's review.

1. **CI builds and checks the zips.** Merging the Clipper's release PR also runs `clipper-firefox-zip` in `.github/workflows/release.yml`. It checks out the `clipper-v<version>` tag, builds `zip:firefox` with the same repository variables as the Chrome job and no `.env`, and fails unless the manifest's `version` equals the tag, `permissions` are exactly `storage`, `activeTab` and `tabs`, there is no `host_permissions` and no `key`, the Gecko ID is `clipper@trakwyn.com` and the bundle contains `CLIPPER_API_URL` and `CLIPPER_WEB_URL`. It then compares the manifest with the previous `clipper-v…` release's **Firefox** zip (not its Chrome one, which asks for other permissions) and fails if `permissions` or any content-script `matches` entry is new, or if that release has no Firefox zip. In that case nothing is attached or submitted: build `zip:firefox` from the tag yourself and submit both zips in the Developer Hub (`store/firefox-listing.md`), after deciding the re-approval prompt is acceptable. Otherwise it attaches `trakwynextension-<version>-firefox.zip` and `-sources.zip` to the GitHub Release, then starts `.github/workflows/clipper-amo.yml` for that tag.
2. **CI submits.** `clipper-amo.yml` downloads the two zips from the GitHub Release (what was checked is what is sent, not a rebuild) and runs `wxt submit` as a **listed**, desktop-only (`--firefox-compatibility firefox`) version with its sources. It runs in the `amo` environment, which has no required reviewer (JEF-458): the environment only keeps the AMO secrets to this job and the default branch. It is a separate workflow so a tag can be submitted again by hand: run "Clipper on Firefox Add-ons" with the tag; it accepts only `clipper-v<major>.<minor>.<patch>`. Do that only for a tag whose zips `clipper-firefox-zip` attached, since the checks live there.
3. **Review** is automatic checks, then a human, and takes hours to days. The reviewer notes are per version and stay manual: if a reviewer asks, answer from `store/firefox-listing.md` (build notes, permission justifications, the demo account). A published version cannot be rolled back, only replaced by a higher one. After approval, install from the AMO page in a clean Firefox profile and check Google and GitHub sign-in against production and a clip.
4. **Hotfixes** follow "After launch" below; the same two jobs submit the new version.

The sources zip is rooted at the monorepo (`wxt.config.ts` `zip`) and was checked to build the same bundle with `pnpm install --frozen-lockfile`. If you change what the build needs from the repo root, change `includeSources` too, then unzip it in an empty directory and build it again.

**One-time setup for the AMO job.**

1. On addons.mozilla.org, Developer Hub → Manage API Keys, generate a JWT issuer and secret (signed in as the add-on's owner).
2. `gh secret set FIREFOX_JWT_ISSUER` and `gh secret set FIREFOX_JWT_SECRET`, as **environment** secrets of `amo` (`--env amo`) so only the AMO job can read them.
3. Settings → Environments → New environment `amo`: limit deployment branches to the default branch, and add no required reviewer (one would hold every release until someone clicked, JEF-458).

`pnpm --filter @trakwyn/extension exec wxt submit --firefox-zip <zip> --firefox-extension-id clipper@trakwyn.com --dry-run` with the two variables in the environment checks the credentials without uploading. To rotate, regenerate the key in the Developer Hub and replace both secrets.

## After launch: compatibility and hotfixes (JEF-417)

A store release cannot be rolled back, only replaced, and an installed copy stays on its version until the browser updates it. Two things break it in the field: the API changing under it, and a job board changing its page.

- **API compatibility.** `src/__tests__/graphqlDocuments.test.ts` validates every document in `lib/api.ts` against the API's schema, printed by `pnpm --filter @trakwyn/api schema:print` (no API to boot), so a renamed or removed field fails CI. It extracts documents with `src/__tests__/support/extractGraphqlDocuments.ts`, a copy of mobile's, and reports an interpolation it cannot resolve rather than skipping the document. A new document goes in `lib/api.ts` as a template string, which the test then covers. What the API may and may not change is in `apps/api/CLAUDE.md` ("Client compatibility"); the `*Mobile` mutations are this app's contract.
- **Seeing a break.** The Clipper health dashboard (`infra/posthog/README.md`, "Clipper health") charts `parser_result` per board and the API, refresh and sign-in failures per `release`, and alerts when one board's parser results pass a daily count.
- **A board changed its page.** Reproduce it first: save the page's markup as a fixture in `src/lib/parsers/__fixtures__` (strip personal data and keep it small), write the failing parser test against it, then fix the parser. The fixtures are how every parser test runs, so the regression stays covered.
- **Shipping an expedited fix.**
  1. Land the fix as a `fix(extension): …` commit and follow "Releasing the Clipper" above: merge the release PR, and the job builds from the tag, uploads and submits. Skip the restricted audience.
  2. Check that no permission or content-script host was added (a re-approval prompt disables it for everyone).
  3. Upload it in the Web Store dashboard and submit for review. The new version number must be higher than the live one.
  4. Ask for an expedited review through Chrome Web Store developer support. Nothing guarantees it, and an ordinary review can take days, so assume the broken version stays live that long. Do not promise users a date.
  5. After it is published, watch the dashboard's `release` split: the fix is working when the old version's line stops growing and the new one's stays flat. Installed copies update on the browser's own schedule, which can take days more.
- **Safari ships separately.** It goes through the App Store and its own review (`package:safari`, above), so a parser fix reaches Safari users later than Chrome users. It reports under the same `release`.
- **A downloaded update is applied when the Clipper is idle (JEF-455).** The background listens for `runtime.onUpdateAvailable` and calls `runtime.reload()` (`lib/updateReload.ts`), so a new version takes effect as soon as the browser has downloaded it instead of at the next unload or restart. A reload empties `storage.session` and closes the popup, so it waits while a popup is open (the popup holds a `RUNTIME_PORTS.POPUP` port, `connectPopupPort`), while any sign-in or token refresh is in flight, and while a tab sign-in is pending in `storage.session` (`hasPendingTabOAuth`). The refresh is the one that matters most: the API has already rotated the token, so losing the new one makes the next refresh look like reuse and revokes the session. **Every new sign-in or refresh path in the background must go through `reloader.track`.** It checks again when a popup closes, when tracked work ends, and every `UPDATE_RELOAD_RETRY_MS`. If the background is unloaded while it waits, Chrome installs the update at that unload anyway. Firefox holds an update for a listening extension until it reloads or the browser restarts, so there an update that was waiting when the event page was suspended stays until the next popup, sign-in, refresh or restart wakes it (an abandoned tab sign-in is the case that leaves nothing to wake it). It does not make the browser check for updates sooner, and there is still no minimum-supported-version signal from the API, so a very old Clipper cannot be told to update. If the compatibility rule is kept, that does not matter.

## Testing

Vitest with `WxtVitest()`, which points `wxt/browser` at WXT's in-memory `fakeBrowser`. Call `fakeBrowser.reset()` in `beforeEach`. It does not restore properties a test deletes: `apiAuth.test.ts` removes `identity` to simulate Safari and puts it back itself.
