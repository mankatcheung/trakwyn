# Releasing the Clipper

The Chrome and Firefox release runbook, moved out of `CLAUDE.md` so it is read when releasing or hot-fixing and not on every task. Paths are relative to `apps/extension/`.

## Releasing the Clipper (JEF-418)

Web Store ID `pnpgngnojencbggokjhpfhmliijakmhe`. A published version can never be rolled back, only replaced by a higher one, and review takes hours to days, so the first public release is staged and every later one follows the same steps. From JEF-419 the release workflow builds the zip and uploads it, and from JEF-429 it submits it for review too (below); a person still publishes it.

1. **Pick the version.** release-please proposes it from the commit types since the last `clipper-v…` tag (root `CLAUDE.md`). To force one, set `"release-as"` on `apps/extension` in `release-please-config.json`; the release PR then proposes exactly that, and **the entry must be removed in the next PR after the release is tagged**, or the next release is forced to the same number. A `Release-As:` footer is not reliable here: the one on #1017's squash commit was ignored (release-please went on proposing `0.3.0`). The first public release is **1.0.0**, forced this way (JEF-418). Never edit a version or `CHANGELOG.md` by hand.
2. **Merge the Clipper's release PR.** It bumps `package.json` and `CHANGELOG.md`, and the workflow tags `clipper-v<version>` and creates the GitHub Release. Check that the PR touches only those two files.
3. **CI builds and checks the zip, then submits it for review (JEF-419, JEF-429, JEF-480).** Merging the release PR starts the `clipper-chrome-zip` job in `.github/workflows/release.yml`, only when release-please reports a Clipper release. It checks out the `clipper-v<version>` tag, builds with `VITE_POSTHOG_KEY` from the repository variable `CLIPPER_POSTHOG_KEY` (the public project key, `terraform -chdir=infra/posthog output -raw project_api_key`), `VITE_API_URL` from the repository variable `CLIPPER_API_URL` (the full production `/graphql` URL, so the URL lives in repository settings and not in the workflow) and `VITE_WEB_URL` from `CLIPPER_WEB_URL` (the web origin), and fails unless the bundle contains both URLs, the manifest's `version` equals the tag and it has no `host_permissions`. It then compares the manifest with the previous `clipper-v…` release's zip and fails if `permissions` or any content-script `matches` entry is new, since nobody looks at the package before it is submitted: release that one by hand (steps 4 and 5, uploading the zip yourself). Otherwise it attaches `trakwynextension-<version>-chrome.zip` to the GitHub Release and starts `.github/workflows/clipper-cws.yml` for that tag. That workflow downloads the zip from the release (what was checked is what is sent, not a rebuild) and runs `wxt submit` in the `chrome` environment, which uploads the package to the existing listing and submits it for review. It is a separate workflow so a tag can be submitted again by hand: run "Clipper on the Chrome Web Store" with the tag (it accepts only `clipper-v<major>.<minor>.<patch>`), and only for a tag whose zip `clipper-chrome-zip` attached, since the checks live there. It passes `--chrome-publish-type DEFAULT_PUBLISH`, so an approved version is published to everyone with no further step (step 5). If `clipper-chrome-zip` fails, nothing reached the store. If the cause is outside the workflow (a missing variable), fix it and re-run the job from the Actions tab. If the cause is in the workflow file, a re-run does not help, since it uses the file from the commit it first ran on: land the fix on `main`, then run **Release** by hand (Actions → Release → Run workflow) with `clipper_tag` set to the existing tag, e.g. `clipper-v1.2.0`. That runs only the Chrome and Firefox zip jobs for the tag, with the current file; release-please does not run, so nothing is tagged or versioned (JEF-454). If only the submission failed (`clipper-cws.yml`), run "Clipper on the Chrome Web Store" with the tag instead, which does not rebuild or touch Firefox; check the dashboard first, since the store refuses a version it has already seen.
4. **Check the package** (the release asset, or `.output/trakwynextension-<version>-chrome.zip` after a local build). In its `manifest.json`: `key` is the listing's public key (`manifest.ts`), `permissions` are `storage`, `activeTab` and `identity`. The job already checks `version` and `host_permissions`, and refuses to submit when `permissions` or content-script `matches` grew since the previous release. If either grew, the store disables the extension for every user until they re-approve it: do not ship that by accident. The job only compares with the previous release, so review the whole list when you change it on purpose. The bundle's only `localhost` is the unused development default in `apiUrls.ts`.
5. **Review and publish.** The job has already submitted the package, and approval publishes it to every user at once: there is no staged rollout and no step for you (JEF-429). A version you submit by hand (when the job refused it, or a first release) is published as you choose in the dashboard's submit dialog. For the first release set the distribution to **Unlisted** or **Trusted testers**. If review asks about a permission, answer from `store/listing.md`; the data-use answers there must still match the privacy policy and what the build does (tokens, `storage`, what is sent), so change them together whenever the Clipper's storage or network use changes.
6. **Verify the published build from the store** once it is live, not an unpacked one: open the store link in a clean Chrome profile, install, then sign in with Google and with GitHub against production and clip a job from LinkedIn and from one other board. Check the extension's ID is the one above.
7. **Watch the health dashboard.** With nothing staged, the new `release` reaches everyone as browsers update, so watch the Clipper health dashboard (`infra/posthog/README.md`) for `graphql_request_failed`, `token_refresh_failed`, `oauth_login_failed` and `parser_result`. A bad version cannot be rolled back, only replaced: ship the fix as in "Seeing a break and shipping a fix" below. (The first public release was a by-hand, staged one.)
8. **Confirm** the published version is the tag's. Installed copies update on the browser's own schedule, so the old version stays in use for days: that is why the API keeps old clients working (`apps/api/CLAUDE.md`, "Client compatibility").

### Web Store credentials for the upload job

The job uses Chrome Web Store API v2, which authenticates as a Google Cloud service account, so there is no consent screen and no refresh token to renew. It reads four secrets of the `chrome` environment, so only `clipper-cws.yml` can read them, and only from the default branch: `CHROME_EXTENSION_ID` (the ID above), `CHROME_PUBLISHER_ID`, `CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL` and `CHROME_SERVICE_ACCOUNT_PRIVATE_KEY` (the key's PEM, multi-line).

To set up:

1. `terraform apply` in `infra/gcp` enables the **Chrome Web Store API** and creates the `chrome-web-store-publisher` service account (no project roles). Create its JSON key with `gcloud`, not Terraform, so it stays out of state (`infra/gcp/README.md`, "Rotate the Web Store key").
2. In the Web Store developer dashboard (signed in as the listing's owner), open **Account** and add the service account's email as a user. This is the one step that cannot be scripted, and without it every call is refused. Copy the **Publisher ID** from the same page.
3. Settings → Environments → New environment `chrome`: limit deployment branches to the default branch, and add no required reviewer (the checks in `clipper-chrome-zip` stand in for one, as for `amo`).
4. Set the secrets on it: `gh secret set CHROME_SERVICE_ACCOUNT_CLIENT_EMAIL --env chrome`, and `gh secret set CHROME_SERVICE_ACCOUNT_PRIVATE_KEY --env chrome < key.pem` with the JSON's `private_key` value written out as a PEM file (`jq -r .private_key key.json > key.pem`), then delete the JSON and the PEM.

`wxt submit --chrome-api-version v2 --dry-run` with the same variables in the environment checks the credentials without uploading. To rotate, create a new key, replace `CHROME_SERVICE_ACCOUNT_PRIVATE_KEY` (in the `chrome` environment) and delete the old key in the Cloud console. Submitting for review and publishing on approval are both automatic (JEF-429). These are plain Actions secrets, not a GitHub App: only the store call needs them, and `clipper-cws.yml` is started by `clipper-chrome-zip` with `gh workflow run`, one of the two events `GITHUB_TOKEN` may start, so the limitation in `release.yml` does not apply.

Safari is a separate release through the App Store (`package:safari`, see `safari/CLAUDE.md`) and is not covered here. Firefox is covered below.

## Releasing to Firefox Add-ons (AMO)

Version and tag are the Chrome ones (steps 1 and 2 of "Releasing the Clipper" above). AMO has no draft or deferred publishing, and no staged rollout: a listed version goes to review, and one that passes goes live. Like the Web Store job since JEF-429, it runs with no manual step, so the checks below are the only ones before AMO's review.

1. **CI builds and checks the zips.** Merging the Clipper's release PR also runs `clipper-firefox-zip` in `.github/workflows/release.yml`. It checks out the `clipper-v<version>` tag, builds `zip:firefox` with the same repository variables as the Chrome job and no `.env`, and fails unless the manifest's `version` equals the tag, `permissions` are exactly `storage`, `activeTab` and `tabs`, there is no `host_permissions` and no `key`, the Gecko ID is `clipper@trakwyn.com` and the bundle contains `CLIPPER_API_URL` and `CLIPPER_WEB_URL`. It then compares the manifest with the previous `clipper-v…` release's **Firefox** zip (not its Chrome one, which asks for other permissions) and fails if `permissions` or any content-script `matches` entry is new, or if that release has no Firefox zip. In that case nothing is attached or submitted: build `zip:firefox` from the tag yourself and submit both zips in the Developer Hub (`store/firefox-listing.md`), after deciding the re-approval prompt is acceptable. Otherwise it attaches `trakwynextension-<version>-firefox.zip` and `-sources.zip` to the GitHub Release, then starts `.github/workflows/clipper-amo.yml` for that tag.
2. **CI submits.** `clipper-amo.yml` downloads the two zips from the GitHub Release (what was checked is what is sent, not a rebuild) and runs `wxt submit` as a **listed**, desktop-only (`--firefox-compatibility firefox`) version with its sources. It runs in the `amo` environment, which has no required reviewer (JEF-458): the environment only keeps the AMO secrets to this job and the default branch. It is a separate workflow so a tag can be submitted again by hand: run "Clipper on Firefox Add-ons" with the tag; it accepts only `clipper-v<major>.<minor>.<patch>`. Do that only for a tag whose zips `clipper-firefox-zip` attached, since the checks live there.
3. **Review** is automatic checks, then a human, and takes hours to days. The reviewer notes are per version and stay manual: if a reviewer asks, answer from `store/firefox-listing.md` (build notes, permission justifications, the demo account). A published version cannot be rolled back, only replaced by a higher one. After approval, install from the AMO page in a clean Firefox profile and check Google and GitHub sign-in against production and a clip.
4. **Hotfixes** follow "Seeing a break and shipping a fix" below; the same two jobs submit the new version.

The sources zip is rooted at the monorepo (`wxt.config.ts` `zip`) and was checked to build the same bundle with `pnpm install --frozen-lockfile`. If you change what the build needs from the repo root, change `includeSources` too, then unzip it in an empty directory and build it again.

**One-time setup for the AMO job.**

1. On addons.mozilla.org, Developer Hub → Manage API Keys, generate a JWT issuer and secret (signed in as the add-on's owner).
2. `gh secret set FIREFOX_JWT_ISSUER` and `gh secret set FIREFOX_JWT_SECRET`, as **environment** secrets of `amo` (`--env amo`) so only the AMO job can read them.
3. Settings → Environments → New environment `amo`: limit deployment branches to the default branch, and add no required reviewer (one would hold every release until someone clicked, JEF-458).

`pnpm --filter @trakwyn/extension exec wxt submit --firefox-zip <zip> --firefox-extension-id clipper@trakwyn.com --dry-run` with the two variables in the environment checks the credentials without uploading. To rotate, regenerate the key in the Developer Hub and replace both secrets.

## Seeing a break and shipping a fix

- **Seeing a break.** The Clipper health dashboard (`infra/posthog/README.md`, "Clipper health") charts `parser_result` per board and the API, refresh and sign-in failures per `release`, and alerts when one board's parser results pass a daily count.

- **Shipping an expedited fix.**
  1. Land the fix as a `fix(extension): …` commit and follow "Releasing the Clipper" above: merge the release PR, and the jobs build from the tag, upload and submit. Skip the restricted audience.
  2. Check that no permission or content-script host was added (a re-approval prompt disables it for everyone).
  3. Upload it in the Web Store dashboard and submit for review. The new version number must be higher than the live one.
  4. Ask for an expedited review through Chrome Web Store developer support. Nothing guarantees it, and an ordinary review can take days, so assume the broken version stays live that long. Do not promise users a date.
  5. After it is published, watch the dashboard's `release` split: the fix is working when the old version's line stops growing and the new one's stays flat. Installed copies update on the browser's own schedule, which can take days more.
- **Safari ships separately.** It goes through the App Store and its own review (`package:safari`, see `safari/CLAUDE.md`), so a parser fix reaches Safari users later than Chrome users. It reports under the same `release`.
