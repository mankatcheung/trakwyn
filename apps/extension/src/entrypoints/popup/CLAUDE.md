# apps/extension/src/entrypoints/popup - popup notes

Loaded when working under the popup. The rest of the Clipper notes are in `apps/extension/CLAUDE.md`. Paths are relative to `apps/extension/`.

## Reading a posting: built-in or AI (JEF-420)

The popup shows two buttons on a job page (`ReadButtons`): **Read with parser** and **Read with AI**. The user chooses per clip; there is no stored setting for it. The popup opens on the built-in result.

- **Parser** is the content script's parsers (`GET_JOB_DATA`). **AI** adds `GET_PAGE_TEXT` (`lib/parsers/pageText.ts`: the main area's text, else the body, capped at `PAGE_TEXT_MAX_CHARS`, the API's `JOB_POSTING_MAX_CHARS`), then the existing `parseJobDescription(text)` mutation (`lib/api.ts`, via `lib/aiRead.ts`). No API change, and no new permission: it works only on the boards the content script matches.
- **"Read with AI" is always on (JEF-451).** The popup cannot cheaply know the plan, and Trakwyn AI (hosted) is Pro-only in phase 1, so `getPopupBootstrap` asks only for `me` and there is no key lookup. A failed read keeps the clip and shows a notice (`Clip.notice`, `noticeCode`). `AI_NOT_CONFIGURED` (a Free user with no key) says to add their own key or upgrade to Pro, and `PLAN_REQUIRED` (a Free user forced onto Trakwyn AI) shows the API's own message; both, like `AI_CREDITS_EXHAUSTED` (the API's message, which names the reset date), carry two links: **Add your own key** (`/settings/ai`) and **upgrade to Pro** (`/settings/plan`). `EMAIL_NOT_VERIFIED` and `AI_TEMPORARILY_UNAVAILABLE` (not emitted by the API yet) have fixed copy; any other code shows its message, so an old build meeting a new code never crashes. The `ai_*_shown/clicked` product events are not sent from the Clipper: reports are operational only with no consent gate (see `src/lib/observability/CLAUDE.md`), so they need a consent decision first.
- **Merge rule** (`lib/parsers/mergeAiResult.ts`): the user asked for the AI, so its answer replaces the parser's for every field it gave; a null or blank AI field never overwrites a parsed one. It merges into the parser's result (`Clip.builtin`), not into an earlier AI read. A clip the AI changed is editable in `ClipCard` before saving, since AI output is a suggestion. **Read with parser** drops the AI result and reads the page again.
- **Failure is never a dead end.** `AI_NOT_CONFIGURED`, `AI_LIMIT_REACHED`, `AI_PROVIDER_ERROR`, `AI_RESPONSE_INVALID`, `EMAIL_NOT_VERIFIED`, `AI_TEMPORARILY_UNAVAILABLE` and `RATE_LIMITED` get their own copy, and `AI_CREDITS_EXHAUSTED` and `PLAN_REQUIRED` pass the API's message through (`AI_ERROR_MESSAGES`); the popup keeps the clip and shows a dismissible notice.
- **Privacy.** Only pressing **Read with AI** sends the page's text, to the user's own LLM provider, or Trakwyn AI on Pro, through Trakwyn's API. Page text and the result are never reported to PostHog; `parser_result` is unchanged.

## Popup startup (JEF-457)

The popup shows the clip from the content script's parsers as soon as it has it, without waiting for the network. The account fills in afterwards.

- **One request.** `getPopupBootstrap` (`lib/api.ts`, operation `PopupBootstrap`) returns the user (no key lookup, JEF-451). Do not add a second startup query: put a field in this one.
- **Order in `App.tsx`.** `init` reads storage, then starts the refresh through the background only when the access token is near expiry or a "Keep me signed in" token can restore the session. `loadReadyScreen` renders the clip and the cached user, then waits for the refresh and the bootstrap. A refused refresh goes to sign-in without `logout`, so an offline browser keeps its persisted token. A 401 calls `logout`.
- **Cached user.** The last confirmed `CurrentUser` is kept in `storage.session` (`STORAGE_KEYS.CACHED_USER`), which content scripts cannot read. `clearSessionAuth` and `clearAuth` remove it with the session. It is only shown: **Save stays disabled until the API confirms the user** (`Account.confirmed`).
- **A load can be superseded.** Signing out, or a new load, bumps `loadId`, so a late answer to an old load is dropped. Read results go through `updateClip`, which ignores them once the popup has left the ready screen.
- **Timings.** `lib/startupTiming.ts` records `popup:<stage>` `performance` measures (`storage`, `refresh`, `readActiveTab`, `bootstrap`, plus `clip-shown` and `account-confirmed` measured from popup open). Read them in the popup's DevTools with `performance.getEntriesByType('measure')` on any build; `pnpm dev` also logs them. Nothing is sent.
- **The background's `scheduleRefresh` is a `setTimeout`**, so it stops when the MV3 worker is suspended, and after an idle spell the popup usually finds the access token expired and asks for a refresh. `alarms` would survive suspension but is a new permission (see `docs/releasing.md`).
