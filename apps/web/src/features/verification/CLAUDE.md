# Email verification wall (JEF-438)

Loaded when working under `apps/web/src/features/verification`. The rest of the web notes are in `apps/web/CLAUDE.md`. Paths are relative to `apps/web/src/` unless stated.

- **The guard is `beforeLoad` on `/_authenticated`**, which awaits `checkEmailVerification()` and redirects an unverified account to `/verify-email-required`, a full-page route outside the layout. It has to be a `beforeLoad` and not a component wrapped around the layout: child route loaders (the dashboard's `queryClient.query`) run regardless and the API refuses each one, so the error boundary would replace the page before a component gate rendered. The cookie check stays synchronous and first. A failed check lets the user through, because the API enforces the wall itself (`apps/api/src/use-cases/auth/CLAUDE.md`); the guard is the polite layer.
- **One request answers the whole guard (JEF-535).** `beforeLoad` calls `checkSessionGate()` (`features/auth/lib/sessionGate.ts`), a single `SessionGate` query for `me { emailVerified deletionScheduledAt onboardingCompletedAt onboardingGoals }`. It writes the answer into the verification and onboarding cache keys below, and skips the request when both are still fresh. The guard also starts the dashboard's four queries (`prefetchDashboard`) without waiting for the gate; the loader joins those in-flight requests, so a verified user's first paint is gated by about two waves, not four. A redirect wastes the prefetch, which is the price of the common case. The chat dock fetches conversations, keys and billing only once it is used (open window, or a pinned pill).
- **One request per session once verified.** `features/verification/lib/emailVerification.ts` caches the answer under one query key, with an infinite `staleTime` once verified and 10 s while not. The wall page refetches on window focus, so verifying in another tab sends the user on to `/dashboard`; `/verify-email-required` itself redirects a verified user there, so it is never a dead end.
- The page offers resend (a 60 s cooldown, a "wait a few minutes" message on `RATE_LIMITED`, a spam-folder hint), "I've verified", a different email (the `requestEmailChange` mutation, which needs the password) and sign out. Registering signs the user in, so the register confirmation links to `/dashboard`, not `/login` (which would only bounce them there).
