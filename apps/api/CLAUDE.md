# apps/api — subsystem notes

Loaded when working under `apps/api`. The layer map, DI shape and cross-cutting conventions are in the root `CLAUDE.md`. Paths below are relative to `apps/api/src/` unless stated.

## Auth

- **Cookies for every client.** Access and refresh tokens are the HttpOnly cookies `trakwyn_access_token` and `trakwyn_refresh_token`. Every auth entry point sets or clears them through `setAuthCookies()`/`clearAuthCookies()` (`http/schema/types/AuthPayloadType.ts`): login, register, TOTP, refresh, reauthenticate, logout, the OAuth callback and delete-account. Cookies are `SameSite=None; Secure`.
- **Bearer fallback.** `buildGraphQLContext.ts` accepts `Authorization: Bearer` when no cookie is present (`cookieToken ?? bearerToken`), for non-cookie clients such as API tokens and the browser extension.
- **`trakwyn_logged_in` hint cookie** (`COOKIES.LOGGED_IN`). It is non-HttpOnly, has the refresh token's lifetime and is what the web app reads to detect a session (see `apps/web/CLAUDE.md`). It only needs to be directionally correct.
- **Deploy prerequisite:** `COOKIE_DOMAIN` must be the shared registrable domain with a leading dot (`.trakwyn.com`). Without it the cookies are host-only on `api.`, the hint is invisible to `www.`, and login "succeeds" while session detection fails.
- **Deploy prerequisite:** `CORS_ORIGIN` must contain the web app's exact origin. `corsPlugin.ts` validates `credentials: true` requests against it, and a mismatch silently breaks cookie delivery. The plugin sets no `allowedHeaders`, which is what lets the clients' `traceparent` through; adding a list without it breaks trace propagation.
- **Mobile** uses `*Mobile` mutations (`http/schema/mutations/mobileAuthMutations.ts`) that return both tokens in the body. `DeviceLabelService` turns the mobile User-Agent into the session label.
- **The browser extension** uses the same `*Mobile` mutations and keeps both tokens in `browser.storage.session` (JEF-383), plus the refresh token alone in `browser.storage.local` when the user ticks "Keep me signed in" (JEF-421), which is why the session lifetime has an absolute cap (below). Its Google/GitHub sign-in is the mobile handoff with a different destination, and `exchangeMobileOAuthCode` redeems it:
  - **Chrome:** `/auth/oauth/:provider/start?platform=extension&codeChallenge=…&extensionId=…` redirects the handoff code to `https://<id>.chromiumapp.org/`. Only IDs in `EXTENSION_OAUTH_IDS` are accepted, and the ID is checked again at the callback, so the redirect host never rests on the cookie alone.
  - **Safari** (no `identity` API, JEF-386): `platform=extension-tab` needs no extension ID. It redirects to this API's own `ROUTES.EXTENSION_OAUTH_DONE`, a static no-store page the extension watches its sign-in tab for. The code is bound to the PKCE challenge, so seeing the URL is not enough to redeem it. CORS allows `safari-web-extension://` origins (`EXTENSION_ORIGIN_SCHEMES`).

## Email verification wall (JEF-438)

A password sign-up can sign in before it verifies its email, but until it does the API refuses nearly everything.

- **Where it is enforced:** `enforceEmailVerification` (`http/emailVerificationGate.ts`) wraps every root Query and Mutation field outside `ALLOWED_WHILE_UNVERIFIED` (`me`, `verifyEmail`, `resendVerificationEmail`, the email-change pair, `logout`, the refresh mutations), in `http/schema/index.ts`. A refused field fails with `EMAIL_NOT_VERIFIED` (403) on its own, so a mixed query still answers `me`. It is on the resolvers, **not a Mercurius `preExecution` hook**, because a hook cannot stop a request: the errors it returns are appended to a result that still runs. `POST /chat/stream` and `POST /mcp` call `AssertEmailVerifiedUseCase` themselves and answer 403. A new unauthenticated-or-recovery mutation that an unverified user needs goes in the allowlist; the test checks every name in it exists.
- **Not traced:** `assertEmailVerifiedUseCase` runs once per root field, so it is in `UNTRACED_USE_CASES`.
- **Auto-verify:** `AUTO_VERIFY_EMAIL` (`infrastructure/config/autoVerifyEmail.ts`) creates a password sign-up already verified and sends no mail. Unset means on outside production, off in production; an explicit `true` in production is for a self-hosted instance with no email provider. Any other value throws. It is read on the first sign-up (`asFunction`), so a test sets it before building its app.
- **OAuth:** a new Google/GitHub account is created verified. When the email already belongs to an account that is **unverified**, `LoginOrSignupWithOAuthUseCase` hands it to the person the provider just vouched for and removes what the squatter set up (password, 2FA, backup email, every session, pending verification links); otherwise registering a victim's address first would leave a back door. A **verified** account still gets `CONFLICT`. The provider must report the email as verified in both cases. GitHub's email is the verified primary from `/user/emails`, never the public profile email.
- `SendEmailVerificationUseCase` does nothing for an already verified account, so a stale "resend" from a second tab mails no live link.
- **Kill switch:** `EMAIL_VERIFICATION_REQUIRED=false` (`infrastructure/config/emailVerificationRequired.ts`) turns the wall off for everyone: `AssertEmailVerifiedUseCase` becomes a no-op and `UserMapper` reports every user as `emailVerified: true`, so web and mobile show no reminder without a client change. Only the exact word `false` turns it off; any other value keeps the wall up, because the flag is read on every authenticated request and must not be able to fail them all. It does not stop sign-ups sending the verification email. In production it is a `plain_env` entry applied with Terraform (`infra/gcp/README.md`, "Day two"), not an ad-hoc `gcloud` update.
- **Backfill for accounts that predate the wall:** `pnpm --filter @trakwyn/api email-verification backfill --before <date> [--dry-run]` (`src/emailVerification.ts`) marks every unverified account created before the cutoff as verified. `--before` is required, so it cannot verify everyone by accident. Run the dry run first: it reports how many accounts the cutoff would cover and how many stay behind the wall. It trusts every address created before the cutoff, including one an attacker registered and never proved, so choose the cutoff on purpose. Like `plan`, it writes the database directly, so a running API shows the old state from its user cache for up to five minutes. A second run changes nothing.

## Captcha and sign-up/sign-in limits (JEF-401)

- **Port and adapters:** `ICaptchaVerifier` (`use-cases/ports/`), implemented by `TurnstileCaptchaVerifier` and `PermissiveCaptchaVerifier` in `infrastructure/captcha/`. `CAPTCHA_PROVIDER` is `turnstile` or `disabled`; unset means Turnstile in production and permissive elsewhere, so dev, CI and e2e need no widget. Turnstile without `TURNSTILE_SECRET_KEY` throws on first use rather than accepting everything. The verifier **fails closed** on a provider outage. `assertCaptcha` turns a refusal into `CAPTCHA_REQUIRED` (no token sent) or `CAPTCHA_FAILED` (token refused).
- **Who is checked:** `register` and `requestPasswordReset` always (before any rate limit is spent, so a bot cannot use up a victim's per-email budget). `login` only once the email or the IP has `RATE_LIMIT.LOGIN_FAILURE` failures in the window, counted by `loginFailureRateLimiter` through `IRateLimiter.isLimited` (a read that spends nothing). Failures are counted for an unknown email too, so the captcha does not reveal whether an account exists. The web login page shows the widget only after it gets `CAPTCHA_REQUIRED`.
- **`enforceCaptcha`:** the web mutations pass `true`. The `*Mobile` mutations (and `requestPasswordResetMobile`, which exists because the shared mutation now needs a token the app cannot produce) pass `false`: no captcha, and they are held to rate limits instead. `registerMobile` gets the tighter `REGISTER_WITHOUT_CAPTCHA` budget. The shared `requestPasswordReset` also skips the captcha when the User-Agent is the mobile app's (`parseTrakwynClientUserAgent`), because builds already in the stores call it with no token; remove that exemption once they are gone. A client that cannot show a widget stays off the captcha path by calling the `*Mobile` mutation, so those budgets are the only thing guarding it.
- **Ceilings that no captcha lifts:** `loginRateLimiter` (every attempt, per email and per IP) and the register budgets. All of them except the failed-login counter use `productionOnlyLimiter` (JEF-400, below), because an integration file signs dozens of users in from one address; the counter stays real so a test can reach the captcha. `registerRateLimiter` is keyed by email as well as IP, and `registerWithoutCaptchaRateLimiter` is the same shape with a `register-without-captcha:` prefix, because the Redis limiter keys on the string alone. `captcha.integration.test.ts` runs the real Turnstile verifier with only `siteverify` stubbed.
- **Deploy order:** the widget is `infra/cloudflare/turnstile.tf`, which outputs both keys (the secret is in that root's state). `turnstile-secret-key` must then have a secret version before the Cloud Run revision that references it starts (`infra/gcp`), and the Vercel build needs `turnstile_site_key` (`infra/vercel`), or the web forms show no widget and the API refuses them.

## Session revocation (JEF-164)

Access tokens are otherwise stateless, so every revocation also writes the `sid` to a blocklist that `AuthenticateRequestUseCase` checks. The writes live in `BlocklistingSessionRepository`, a decorator over `DrizzleSessionRepository` (the same inner/outer DI shape as `Cached*Repository`), so no call site has to remember. The store is Redis or an in-process map, chosen by `CACHE_PROVIDER`. **It fails open:** a store error means "not revoked" (at most the 15-minute token lifetime), and the DB `revokedAt` is still enforced at refresh.

**Session lifetime (JEF-422).** A session slides forward 7 days (`SESSION.TTL_MS`) on every refresh, and `SESSION.ABSOLUTE_TTL_MS` (90 days from `createdAt`) caps that. `RotateRefreshTokenUseCase` refuses a refresh past the cap with the same `UNAUTHORIZED` as an expired session (no revocation, no reuse log) and clamps the new `expiresAt` to it in all three branches (normal, grace window, legacy adoption). Without it a refresh token that keeps being used, or a stolen one whose owner stopped refreshing so reuse is never seen, never expires. A session already older than the cap is signed out at its next refresh.

## MCP server

`POST /mcp` (`http/routes/mcp.routes.ts`) is JSON-RPC 2.0, POST-only with no SSE or session handling. The route owns transport and auth; protocol logic lives in `interface-adapters/mcp/McpController.ts`.

- **Protocol version (JEF-468):** `initialize` answers with the client's `protocolVersion` when it is in `MCP.SUPPORTED_PROTOCOL_VERSIONS` (`2025-03-26`, `2024-11-05`), otherwise with `MCP.PROTOCOL_VERSION` (`2025-03-26`, the first with tool annotations). `2025-06-18` is not offered: it would oblige the route to validate an `MCP-Protocol-Version` header on every request.
- **Annotations (JEF-468):** every tool in `tools/list` carries `annotations`, derived in `mcp/mcpToolDefinitions.ts` and never written per tool: `readOnlyHint` is `access === 'read'`, `destructiveHint` is the catalogue's optional `destructive: true` tag (only `trash_application`), `idempotentHint` is true for `update_*`. They are hints for a client deciding whether to ask the user; the scope check in `tools/call` is still the boundary. A new tool that removes something from the user's view gets `destructive: true`.
- **Write dispatch:** every write tool is handled in `mcp/writeToolHandlers.ts`, a map typed `Record<WriteToolName, …>`, so a write tool added to the catalogue without a handler fails typecheck. Read tools stay in the controller's switch. Argument narrowing (`toStr`, `toDate`, `toAmount`, `toOneOf`) is `mcp/toolArgs.ts`; a closed domain set (round type and outcome, offer period) is declared once in the catalogue, advertised as an `enum` and checked again by the handler. Handlers pass only the caller's `userId`; the use case does the ownership check.
- **Errors:** a use-case failure with `NOT_FOUND`, `FORBIDDEN` or `PLAN_REQUIRED` is `INVALID_PARAMS` with the code in `error.data.code`; anything else is `INTERNAL_ERROR`. `create_offer` is the one gated write (`offers`); `update_offer` follows `UpdateOfferUseCase`, which is ungated so an offer recorded on Pro stays editable after a downgrade.
- **Call limits (JEF-465):** `tools/call` spends one call from `RATE_LIMIT.MCP_TOOL_CALL_READ` or `MCP_TOOL_CALL_WRITE` (by the tool's `access`; 300 and 60 per 5 minutes), per credential: `AuthenticateMcpRequestUseCase` returns a `tokenId` prefixed `api:`/`oauth:`, and the controller falls back to `user:<id>` without one. The check sits after the scope refusal (a refused call spends nothing) and before dispatch; `initialize`, `tools/list` and unknown tool names are not counted. A spent budget is JSON-RPC `RATE_LIMITED` (-32029) with `data.retryAfterSeconds` (the whole window, an upper bound) and the `rate_limited` tool outcome. The two limiters share one Redis keyspace, hence the `mcp-tool-call-<access>:` key prefix.
- **No hard deletes over MCP.** `trash_application` is the soft delete (restorable from Trash for 30 days); permanent deletes and bulk operations are not exposed.

- **Auth:** `AuthenticateMcpRequestUseCase` accepts API tokens of either scope (`read`/`full`) and rejects JWTs. GraphQL's `AuthenticateRequestUseCase` requires `full`, so a `read` token reaches MCP only. Every tool is scoped to the caller's `userId`.
- **Access tags (JEF-176):** each tool is `access: 'read' | 'write'`. `tools/list` hides write tools from `read` tokens, and `tools/call` **refuses** them (the refusal is the security boundary). The tag is stripped before it goes over the wire.
- **Catalogue:** `interface-adapters/llm/toolCatalogue.ts` (JEF-177). `use-cases/` never imports it; `ChatWithAssistantUseCase` gets `chatTools` injected. `http/di` decides exposure: `MCP_TOOLS` is the whole catalogue, and chat gets `CHAT_TOOLS` (reads only, since chat has no scope to gate on).
- **When adding a tool,** add it to `TOOL_CATALOGUE` _and_ to the dispatch of every surface that exposes it (MCP: the controller's switch for a read tool, `WRITE_TOOL_HANDLERS` for a write tool; also the README's tool table). The parity tests catch a tool that is advertised but not handled.
- **Write attribution (JEF-466):** `AuthenticateMcpRequestUseCase` returns an `actor` (`McpActor`, `use-cases/shared/mcpActor.ts`: `source: 'mcp'`, `apiTokenId`, `apiTokenName`) beside the scope. For an API token that is its id and name; for an OAuth grant it is the grant (family) id, which is what the user revokes, and the client's registered name. The route hands it to `McpController.handle`, which passes it to the three write handlers whose use cases log to the activity timeline (`update_application`, `create_note`, `create_interview_round`) as `actor`; they spread `actorPayload(actor)` into the log payload, so a write made in the app logs exactly what it did before. A new write tool whose use case appends to `IActivityLogRepository` must take `actor` the same way. The observer also gets the id as `ToolCallMeta.tokenId` and records `app.mcp.token_id` on **write** calls only, which covers the writes with no activity log (skills, education, work experience). Web's `ActivityTab` shows "via <name> (MCP)".
- **Tool-call observation (JEF-365):** `McpController.callTool` and `chatAssembly.executeChatTool` run every call through `IToolCallObserver.observe(meta, run)` (`use-cases/ports/`). The surface reports how the call ended through the recorder it is handed: `succeeded`, `failed`, `invalidParams`, `rateLimited` or `refused(userId)`. The OTel implementation is `infrastructure/observability/ToolCallObserver.ts`, registered in `http/di/infrastructure.ts` with the whole catalogue. A new dispatch path must go through `observe`; the parity tests in `McpController.test.ts` and `chatAssembly.test.ts` check every catalogue tool does.

## Storage

`STORAGE_PROVIDER` is `local` (disk, dev) or `vercel-blob` (prod). The upload flow is `requestUploadUrl`, then the client uploads directly, then `confirmDocument`.

- Blob returns a client token for `@vercel/blob/client`'s `put()`.
- Local returns a URL under `/uploads/_upload/*` (registered in `buildApp.ts` when `STORAGE_PROVIDER === 'local'`). Web's `DocumentsTab` detects `/_upload/` and `PUT`s to it with `fetch`. `corsPlugin.ts` lists `PUT` explicitly for this.
- **Documents are read through the API, never from a storage URL (JEF-51).** `Document.url` is `GET /documents/:id/file?token=…` (`http/routes/documentFile.routes.ts`), built by `DocumentFileLinkService` behind `IDocumentFileLinks`. The token is `<expiry>.<HMAC>` over the document id and expiry under `JWT_SECRET`, valid for `DOCUMENT_FILE_LINK.TTL_S` (an hour: web reads `url` from a list it may have fetched long before the click), so it opens that one document and nothing else. It carries its own credential because the clients that open it (`<iframe>`, `<img>`, mobile `Linking.openURL`) cannot send one. A resolver only builds a link for a document the caller owns; that is the ownership check, so a new code path that returns a `DocumentDTO` must use `documentFileLinks`, not `getSignedUrl`. The route serves the file through `IStorageProvider.getObject` for both providers. The token is a credential, so it is kept out of telemetry: the http instrumentation's `redactedQueryParams` (`tracing.ts`) blanks it on spans, and `index.ts`'s `req` log serializer blanks it with `redactDocumentToken`. Keep both if either is touched.
- **Server-side readers use `getObject` too** (`ExtractDocumentTextUseCase`, and `ComputeResumeMatchScoreUseCase` and `ComputeResumeAtsScoreUseCase` through `loadDocumentText`, which wraps `readStoredObject` for a bounded read), so they need no URL and keep working when the store becomes private.
- **ATS-readiness score (JEF-395).** `computeResumeAtsScore` scores a resume's extracted text with `scoreResumeText` (`use-cases/shared/`): pure, deterministic, no AI key. The latest result is saved per resume (`ResumeAtsScore`, one row per draft or uploaded file, replaced on a re-check) so it survives a reload; `resumeAtsScores(applicationId)` reads them back with `isStale`, set when a draft's text no longer hashes to `resumeTextHash` (the same rule as the match). Clients must refetch it when a draft is saved. The weights, length range and bands are one `ATS_SCORE` block in `use-cases/constants.ts` and must sum to 100. A scan or image (no extractable text) is `readable: false` with score 0, not a low score, and the other checks are not run. It judges text only, so layout (columns, tables, headers) is not checked. The PDF extractor emits Markdown, so heading and bullet matching tolerate `#`, `**` and `-`.
- **`getSignedUrl` is for avatars only.** They are meant to be seen by other users, so they stay on a public URL. Local read-back is `GET /uploads/*` through `LocalStorageProvider.openObject`, which refuses keys outside `uploads/` and serves only `users/<id>/avatar/…`; every other key is a 404. It is unauthenticated and deliberately not on `IStorageProvider` (JEF-343).
- **Total document storage per user is capped (JEF-425).** `CONTENT_LIMITS.DOCUMENT_STORAGE_LIMIT_BYTES` (100 MB) is counted in `user.documentBytes`, kept transactionally like `applicationCount`: `DrizzleDocumentRepository.create` reserves the bytes with one conditional `UPDATE` (so simultaneous uploads cannot both pass the limit) and throws `QuotaExceededError` with the used and limit values; `delete` releases them; `DrizzleApplicationRepository.delete` releases the sum of the application's documents, because they cascade. Trash counts until it is purged. `requestUploadUrl` takes an optional `sizeBytes` and refuses a full account before the upload; `ConfirmDocumentUseCase` reads the real size with `IStorageProvider.headObject` and refuses a mismatch, so a client cannot under-report. The limit reaches clients as `me.storageUsedBytes`/`storageLimitBytes`, taken from the user's entitlements by `UserMapper`. `DrizzleDocumentRepository.create` takes the limit as `storageLimitBytes`, which `ConfirmDocumentUseCase` and `ExportDocumentDraftToPdfUseCase` read from the owner's entitlements (JEF-344), so a Pro user's 2 GB is enforced by the same one `UPDATE`.
- **Two Blob stores, chosen by key (JEF-51).** `storageAccessFor(key)` (`use-cases/shared/storageAccess.ts`) is the one place that decides: `users/<id>/avatar/…` is `public`, everything else is `private`, so a new kind of file is private unless it opts out. `VercelBlobStorageProvider` sends each key to the store of that access, with that store's token (`BLOB_PUBLIC_READ_WRITE_TOKEN` or `BLOB_PRIVATE_READ_WRITE_TOKEN`). **A missing private token throws; it never falls back to the public store**, so a secret that was not loaded cannot make a document public. `getSignedUrl` throws for a private key for the same reason: only avatars have a storage URL.
- **The client's `put()` must match the store.** A client token is for one store, and `put()` is refused if its `access` differs. `requestUploadUrl` and `requestAvatarUploadUrl` therefore return `access`, and web passes it to `put()` (`blobAccessOf`, which treats anything but `private` as `public` so an older API still works).

## CV import (JEF-461)

Reads an uploaded CV into work experience, education and skills for the user to review, then saves what they ticked. **The file is never stored.**

- **Two steps, two transports.** `POST /profile/cv-import` (`http/routes/cvImport.routes.ts`) reads the file and returns entries; nothing is written. `importCvProfile` (GraphQL) takes back the ticked, edited rows and creates them in one transaction. Multipart cannot ride GraphQL without raising the body limit for every operation, hence the route.
- **Nothing is stored.** The buffer goes to `DocumentTextExtractor`, then the user's own model, then is dropped. `ParseCvUseCase` has no storage dependency, the route never logs the body or the filename, and `cvImport.routes.integration.test.ts` spies every `IStorageProvider` method and fails a test that calls one. The text goes to the user's provider (the dialog says so); it is not stored by Trakwyn.
- **Multipart is scoped.** `registerCvImportRoute` registers `@fastify/multipart` (one file, no other fields, `CV_IMPORT.MAX_BYTES`) in a plugin scope of its own, so no other route parses it; `/graphql` treats a multipart body like any unsupported type. Fastify's `bodyLimit` does **not** apply to a streamed multipart body, so the per-file limit is the bound (a larger file is cut off and answered 413). The route reads every part before spending anything, so a second file or a stray field is a 400 and never reaches the model.
- **The upload header is the CSRF guard.** Auth cookies are `SameSite=None` and a multipart POST is a "simple" cross-site request, so without a preflight another site could post a file with the visitor's cookie and spend their AI key. The route refuses a request without `CV_IMPORT_UPLOAD.REQUIRED_HEADER` (a custom header forces a preflight, which `corsPlugin.ts` answers only for listed origins). `/chat/stream` needs no such header because its JSON body already forces one. The route also applies the verification wall and shares `authenticateRoute` with the chat stream.
- **File checks run in `ParseCvUseCase`, before the rate limit,** so a wrong file does not spend the user's budget (`cvImportValidation.ts`: type, the bytes actually received, then the content's signature). It uses `CV_IMPORT_MIME_TYPES`, not `ALLOWED_DOCUMENT_MIME_TYPES`, because that list admits legacy `.doc`, which the extractor cannot read. The web app repeats the type and size checks for speed; these are the ones that count.
- **Output budget.** `CV_IMPORT.MAX_OUTPUT_TOKENS` is the provider ceiling (`LLM.MAX_OUTPUT_TOKENS_CAP`). The default (512) cuts off the JSON of an ordinary CV, and every other caller shares that cap. A very long CV can still reach it and fails as "the AI ran out of room"; raising the cap is a cost decision for every AI feature, not part of this one.
- **What the model says is not trusted.** Dates are normalised to `YYYY-MM` (`cvProfileNormalization.ts`); an entry without its required fields is dropped; text is clipped to `CV_IMPORT`'s limits; proficiency is kept only if it is one of the four levels the profile's picker knows. The CV is wrapped with `wrapUntrustedContent`.
- **Imports are not de-duplicated by the API.** `ParseCvUseCase` flags `alreadyInProfile` (company + title + start month, institution + degree, skill name, all case-insensitive) so the review step starts those unticked, and the web dialog guards a double submit; calling `importCvProfile` twice with the same rows adds them twice.
- The fake LLM route answers the CV prompt with a canned profile, found by `CV_IMPORT_PROMPT_TASK` in the system prompt, so e2e needs no key (`e2e/cv-import.spec.ts`).

## Plans and entitlements (JEF-344)

Free and Pro. This is the tiering half; taking payment is JEF-426 (see Billing below), which sets the same user fields from a provider's webhook.

- **State vs policy.** The user row holds only `plan` (`free`/`pro`), `planExpiresAt` and `planSource` (`subscription`, `pass`, `trial`, `grant`). What a plan allows is code: `PLAN_LIMITS` and `PLAN_FEATURES` in `use-cases/constants.ts`, whose Free column _is_ `CONTENT_LIMITS`. `resolveEntitlements(plan, planExpiresAt, now)` (`use-cases/plans/`) is pure, and `effectivePlan` (domain) reads an expired pass or trial as Free, so nothing has to run to downgrade a user. Data is never touched by a downgrade: a user over a cap can read, export and delete, not add.
- **`PLANS_ENFORCED` (default off) is read in one place**, `EntitlementService`. Not enforced means every Pro feature on, **but the caps that already existed stay** (50 applications, 100 MB): lifting them would loosen a deployed system the moment this shipped. Every self-hosted instance runs this way. No use case checks the flag.
- **Gating is `entitlementService.assertFeature(userId, feature)` as the first line of a use case** (`PlanFeature`: `notifications`, `analytics`, `offers`, `shareLinks`, `apiAccess`, `mcpAccess`). It throws `PlanRequiredError` (`PLAN_REQUIRED`, 403 through `fromCodedError`). Gated: the offer and analytics aggregates and `CreateOfferUseCase`, `CreateShareLinkUseCase`. Reading your own data stays open (per-application offers, export). `featureGating.test.ts` asserts each refuses before touching any other dependency, so a new gated use case gets a row there.
- **Jobs skip, they do not fail.** The digest, reminder and push jobs skip a Free user (counted as `skipped`) without sending, without creating an inbox row and without marking a round notified, so an upgrade before it passes still gets it.
- **MCP is on for every plan; the GraphQL API with a token is Pro (JEF-442).** `mcpAccess` is true in both `PLAN_FEATURES` columns and `apiAccess` only in Pro. Any plan may create an API token (`CreateApiTokenUseCase` is not gated). `ValidateApiTokenUseCase.execute(rawToken, surface)` checks the feature of the surface it is serving: `'mcp'` needs `mcpAccess` (`AuthenticateMcpRequestUseCase`, for API tokens and the OAuth branch), `'graphql'` needs `apiAccess` (`AuthenticateRequestUseCase`). So a Free user's token works on `/mcp` and is refused on GraphQL, and it is not deleted, so an upgrade brings the GraphQL side back.
- **AI actions are not limited by plan (JEF-442).** They run on the user's own key, which the provider bills directly, so neither plan has an allowance; the only AI limit is a key's own `monthlyTokenLimit` (JEF-258) in `LimitEnforcingLLMProviderFactory`. There is no `aiActionsPerMonth` limit or `aiActionsThisMonth` usage any more. If Trakwyn ever hosts a model it pays for, that needs its own allowance.
- **Caps are passed in, not read.** `CreateApplicationData.applicationLimit` (`null` = none) and `CreateDocumentData.storageLimitBytes` come from the owner's entitlements, and the repositories still reserve against them in one conditional `UPDATE`. A new caller of either `create` must pass one. The per-parent counts follow the same rule (JEF-440): `CreateDocumentData.documentsPerApplicationLimit`, `CreateInterviewQuestionData.questionsPerRoundLimit` and `CreateMockInterviewQuestionData.mockQuestionsPerRoundLimit` are passed by the create use cases from `CONTENT_LIMITS` (they do not vary by plan), and no repository reads `CONTENT_LIMITS` for a cap.
- **`billingStatus`** (`GetBillingStatusUseCase`) returns the plan, `enforced`, the user's features, limits and usage, and a `catalogue` of both plans so a client can compare them without copying the numbers. `me.storageLimitBytes` follows the plan.
- **The user row is cached** (`CachedUserRepository`, five minutes). The repositories bust it on create/delete of an application and a document, and on `update`. A change made by the operator command goes around the cache, so it shows within five minutes.
- **Operator command:** `pnpm --filter @trakwyn/api plan set --email <email> --plan <free|pro> [--days <n>]` records a `grant`; `plan grant-trial [--days <n>] [--dry-run]` gives every user who has never had a plan a Pro `trial` (30 days by default, `PLAN_TRIAL.LAUNCH_DAYS`), so it is run on the day enforcement is switched on, not in a migration, and a second run grants nothing twice. Both write to `DATABASE_URL` directly (`src/plan.ts`).
- **Launch order:** ship with enforcement off, build payment (JEF-426), then set `PLANS_ENFORCED=true` and run `plan grant-trial`.

## Billing (JEF-426)

The payment side of the plans above. A **merchant of record** is the seller, so the owner (a UK sole trader) does no VAT or sales-tax filing. Polar is the chosen provider.

- **Port and adapters:** `IBillingProvider` (`use-cases/ports/`): `createCheckoutSession`, `createPortalSession` and `parseWebhook` (signature check over the raw bytes, then a provider-neutral `BillingWebhookEvent`). `FakeBillingProvider` serves dev, CI and e2e; `PolarBillingProvider` is the real one (JEF-432). `BILLING_PROVIDER` is `fake` or `polar`; unset means fake outside production and a throw on first use in production. Registered with `asFunction`, so a missing key fails on first use. Nothing outside `infrastructure/billing/` names a provider.
- **Polar adapter (JEF-432).** Plain `fetch` pinned to `Polar-Version` (`POLAR.API_VERSION`) plus the `standardwebhooks` package, not Polar's SDK, which is versioned by import path. `buildBillingProvider` needs `POLAR_ACCESS_TOKEN`, `POLAR_WEBHOOK_SECRET`, `POLAR_SERVER` (`sandbox` or `production`, deliberately no default) and the four `POLAR_PRODUCT_*` ids, and names every missing one. The checkout carries the Trakwyn user id as `external_customer_id` and `metadata.userId`; a returning buyer is sent with `customer_id` instead, so Polar does not create a second customer. A Polar refusal is thrown as the status, the path and, for a validation error, the field names with Polar's messages (at most five). Those messages can quote what we sent, and the error is logged to Axiom and Cloud Logging outside the erasure path (JEF-348), so the buyer's email and user id are blanked from them first (`redacted` in `PolarBillingProvider.ts`).
- **Polar event mapping** (`polarWebhookEvents.ts`, tested in `polarWebhookEvents.test.ts`): `subscription.active` and `subscription.uncanceled` start a plan (the second clears a cancellation's end date); `subscription.canceled` ends it at `ends_at` or the period end; `subscription.revoked`, sent when payment retries run out, ends it at `ended_at` (a lapse is a cancellation, not a reversal). `past_due` changes nothing, so Pro continues through Polar's retries (about 21 days) before the revoke. A paid one-off order is a pass, with months from its product id; an unknown one-off product **throws**, so a payment is never silently dropped. A subscription's own orders, first or renewal, are `ignored`, so a renewal extends nothing. Only a fully refunded order is `payment_reversed`; a partial refund is ignored. Polar has no dispute event (see Known gaps below). Any event type not listed is `ignored`, and a known one whose payload cannot be read **throws** (a 500), so Polar redelivers and the log shows it.
- **The webhook's event id is Polar's `webhook-id`,** which Standard Webhooks keeps across retries; that is what `BillingEvent` dedupes on. Timestamps older than five minutes are refused by the library, so a captured delivery cannot be replayed later.
- **The client names a plan, the API picks the price.** `CreateCheckoutSessionUseCase` turns `monthly` into `founder_monthly` when `now - max(createdAt, BILLING_LIVE_FROM) < 60 days`, so the founder price cannot be asked for or stacked. An active subscriber is refused (`CONFLICT`) rather than sold a pass or a second subscription; a pass holder may subscribe (the pass is forfeited, the Plan page says so) or buy another pass (it extends).
- **The webhook is the only thing that sets a paid plan.** `POST /billing/webhook` (`http/routes/billing.routes.ts`) sits in its own plugin scope with a buffer parser, because the signature is over the bytes sent and the app-wide JSON parser would re-encode them. `HandleBillingWebhookUseCase` records the provider event id in `BillingEvent` _in the same transaction_ as the plan change: a replay finds the id and does nothing, a failure leaves neither so the provider's retry applies it once. A bad signature is 401; any other failure is 500 so the provider redelivers. Rules: subscription starts → `pro`/`subscription`/no expiry; pass → `pro`/`pass`/`max(now, current pass expiry) + 3 or 6 months`; cancellation → `planExpiresAt = end of paid period` (only for the subscription the user is on); refund or chargeback → free now (only when it reverses what the user is on). An event naming no known user is recorded and ignored, so it is not retried forever.
- **User columns** `billingCustomerId` and `billingSubscriptionId` are provider-neutral. `BillingEvent` cascades with its `User`.
- **Known gaps and rules (JEF-433 sandbox run; runbook in `infra/polar/README.md`).**
  - **Escalated disputes send no event and have no endpoint.** Only a refund Polar issues to _prevent_ a dispute arrives (as `order.refunded`, handled). An escalated one leaves the user on Pro, so the operator downgrades by hand with `plan set --plan free`.
  - **A refund does not end a Polar subscription.** The operator refunds the order in full and then revokes the subscription immediately; cancelling at period end leaves it active, blocks resubscribing and keeps renewing (renewals are ignored, so the customer would pay and stay Free).
  - **Deleting an account revokes the Polar subscription first (JEF-439).** `DeleteAccountUseCase` calls `IBillingProvider.revokeSubscription` (`DELETE /subscriptions/{id}`, token scope `subscriptions:write`) when the user row has a `billingSubscriptionId`, after the password and step-up checks and before the blobs and the row go. If Polar cannot be reached or refuses, the deletion stops with `SERVICE_UNAVAILABLE` ("We could not cancel your subscription. Try again, or contact support.") and nothing is deleted; the provider's own error goes to the log. A 403 (already revoked) or 404 from Polar counts as done, and a 409 (pending an update) is a retry. Users without a subscription never read the billing provider, which matters because it throws when `BILLING_PROVIDER` is unset. A subscription whose `billingSubscriptionId` was already cleared (a refund without a revoke) is not found by this, so the runbook's refund rule still applies.
  - **`createCheckoutSession` does not check `PLANS_ENFORCED`; only the UI hides the buttons.** Anyone signed in can call it by hand, so a sandbox provider on production lets a user buy Pro with a test card. Test against production in one sitting and revert (runbook, "Switching an environment on, and off again").
- **Web:** checkout and the portal are on the Plan page (`/settings/plan`), shown only where `PLANS_ENFORCED` is on. The mutations are `createCheckoutSession(plan)` and `createBillingPortalSession`; both return a `url` to send the browser to.
- **Dev:** with the fake provider, "checkout" returns to the Plan page with `?fake_checkout=<product>`; to complete a purchase post a body signed with `signFakeWebhook` (`infrastructure/billing/FakeBillingProvider.ts`) to `/billing/webhook`, as `billingWebhook.integration.test.ts` does. Provider setup and launch steps are in `infra/polar/README.md`.

## Email

`EMAIL_PROVIDER` is `brevo` (the default) or `console`. `ConsoleEmailService` logs each mail, including its confirm/reset URL. `BrevoEmailService` throws on a blank key, and mail-dependent flows (`RequestEmailChangeUseCase` and friends) surface that as a 500. Only `RegisterUseCase`'s verification send is best-effort.

**Verification-mail abuse limits (JEF-400).** Sign-up is the one unauthenticated route that sends mail, so it is the one a bot can use to spend the shared Brevo quota. Three limiters guard it: `registerRateLimiter` (5 sign-ups per hour per IP, checked in `RegisterUseCase` before the hash and the lookup), and in `SendEmailVerificationUseCase`, `emailVerificationUserRateLimiter` (3 per hour per account) and `emailVerificationGlobalRateLimiter` (100 per day across everyone, which keeps a distributed abuser from starving password-reset mail). Both are checked before the old token is deleted, so a throttled request leaves the emailed link working. The global budget being spent does not block sign-up: `RegisterUseCase` already swallows a failed send, so the account is created and the user can resend later. **The IP and global limits are enforced only when `NODE_ENV=production`** (`productionOnlyLimiter` in `http/di/rate-limiters.ts`); elsewhere their ceiling is `RATE_LIMIT_RELAXED_MAX_ATTEMPTS`, because dev, e2e and the integration suites sign up dozens of users from one address. `di-modules.test.ts` pins both behaviours.

## Database (JEF-342)

- **Drivers:** `DATABASE_URL`'s scheme picks the driver in `infrastructure/db/createDb.ts`. `postgres://` uses a `pg` pool; `pglite:<dir>` or `pglite:memory` runs PGlite in-process. Local dev uses `pglite:./.pglite` (one process at a time), CI e2e uses Postgres 17 and tests use in-memory PGlite. Repositories are typed against `DrizzleDb`/`DrizzleTransaction`.
- **Production** is Neon (`aws-eu-central-1`, Free plan, 0.25 CU, scales to zero after 5 minutes; compute and branch in `infra/neon`). The API uses the **pooled** URL (Secret Manager `database-url`); migrations use the **direct** URL (`PRODUCTION_DATABASE_URL`), since the pooler runs in transaction mode. Stay on `pg`, not `@neondatabase/serverless`, which cannot run the interactive transactions. Pool policy is `DATABASE` in `infrastructure/config/constants.ts`, and the pool's `'error'` handler keeps Neon's idle-socket closes from crashing the process.
- **Schema** is `infrastructure/db/schema.ts`: timestamps are `timestamptz(3)` (`schema/columns.ts`); salaries and `monthlyTokenLimit` are `bigint`. `pnpm db:generate` writes into `drizzle/` (baseline `0000_postgres_baseline`). `applyMigrations.ts` applies them in one transaction under an advisory lock.
- **Transactions are ambient (JEF-427).** `ITransactionManager.run` stores the transaction in `AsyncLocalStorage`, and every `Drizzle*Repository` reads it through `getClient(db)`, so a use case never passes a handle. A use case whose writes must stand or fall together (several repositories, or a token marked used plus what it unlocks) wraps them in `runInTransaction(this.deps.transactionManager, …)` (`use-cases/runInTransaction.ts`; the dependency is optional so mock-repository unit tests need no manager). Rules: a throw out of the callback rolls back everything in it, so **security side effects that must survive a refusal (token-family revocation, reuse events) stay outside it**, and the callback returns a value instead of throwing (see the two MCP token use cases); email, storage and LLM calls stay outside too. A new repository must use `getClient` (`repositoryTransactions.test.ts`), and a new multi-write use case gets a rollback test in `useCaseTransactions.test.ts`, which uses the real repositories because mocks cannot show a rollback.
- **Postgres gotchas:** `LIKE` is case-sensitive (use `ilike`); cast a bare parameter inside `CASE` (`${index}::integer`); `count`/`sum` come back as `number`, but `numeric` (`avg`, `sum` over `bigint`) stays a string.
- `src/copyFromTurso.ts` and `infrastructure/db/copyToPostgres.ts` are the one-off Turso copy. Delete them, and their `dependencyRule.test.ts` root exemption, once Turso is retired.

## Observability (JEF-129)

- **Axiom via OTel** (`infrastructure/observability/tracing.ts`), **production only** (JEF-345): `isObservabilityEnabled` needs `NODE_ENV=production` plus `AXIOM_TOKEN`/`AXIOM_DATASET`. **One dataset per signal** (JEF-373): traces go to `AXIOM_DATASET`, logs to `AXIOM_LOGS_DATASET` and metrics to `AXIOM_METRICS_DATASET`. Leaving either of the last two unset disables that signal only. An Axiom correlation group links a trace to its log lines (`infra/axiom/README.md`), so don't merge the datasets back to get that link.
- **Release (JEF-362):** one value across all three apps, the full commit SHA the artifact was built from, or `dev` when there is none. The API reports it as the OTel resource's `service.version` (so every span, log and metric carries it) from `APP_RELEASE`, which `deploy-api` bakes into the image as a Docker build arg; it is not a Cloud Run env var, because Terraform owns those. Web sends it as PostHog's `release` from `VITE_APP_RELEASE`, set to `github.sha` by `.github/actions/vercel-deploy-production` (`vite.config.ts` falls back to `VERCEL_GIT_COMMIT_SHA` for builds on Vercel). Mobile registers it as a PostHog `release` super property, read from `extra.release`, which `app.config.ts` fills from `EAS_BUILD_GIT_COMMIT_HASH` or `APP_RELEASE`. Filter Axiom by `resource.service.version` and PostHog by `release` with the same SHA.
- **The SDK starts from a preload** (JEF-346): `node --import ./dist/instrumentation.js dist/index.js`. ESM hoists imports and only the `import-in-the-middle` loader can patch `graphql`/`pg`/`ioredis`/`undici`/`http`. Do not move the start into `index.ts`.
- **Root span:** it is renamed to `POST /graphql <op>` (`graphqlOperationSpanName.ts`, via a Mercurius `preExecution` hook) or `POST /mcp tools/call <tool>` / `POST /mcp tools/list` (`interface-adapters/mcp/mcpOperationName.ts`, from the MCP route). Both go through `operationSpanName.ts`. Only our own method and tool names reach a span name; anything else is `unknown`. `formatError` marks it `ERROR` with `error.type` for server faults only (not `NOT_FOUND` or a wrong password), and **never with a message**, since Drizzle errors embed query parameters.
- **Invalid documents (JEF-472):** a document that fails validation or parsing is a stale client (JEF-417), not a server fault. Mercurius throws one `MER_ERR_GQL_VALIDATION` error wrapping the real list, which `buildApp.ts`'s `errorFormatter` unwraps with `formatValidationFailure` before `formatError` sees it (`formatError` maps one error to one, and used to turn the wrapper into "Internal server error" for the client). Each message goes back as a `VALIDATION` error (HTTP stays 200). One `graphql.validation.failed` line is logged at `warn` with the sanitised `operationName` (shaped like a GraphQL name, or dropped), `client`/`clientVersion`, the count and the first ten messages clipped to 200 characters; `trakwyn.graphql.validation_failures` counts it by `client` (`mobile`, `extension`, `other`) and `client_version` (mobile only). The root span is named `POST /graphql validation_failed`, not after the operation, because the `preExecution` hook never runs and the name must come from a bounded set; the client's name is the `graphql.operation.name` attribute. The span is **not** `ERROR`, so `graphql_error_rate` ignores it. Messages can quote a literal written inline in the document; variables are never read.
- **Tool spans (JEF-365):** each MCP and chat tool call gets a `mcp.tool <name>` / `chat.tool <name>` span with `app.tool.name`, `app.tool.access`, `app.tool.surface`, `app.tool.outcome` (`ok`/`domain_error`/`internal_error`/`refused`/`invalid_params`), `app.tool.result_bytes` and, on MCP, `app.mcp.token_scope`. Only `internal_error` marks the span `ERROR`. **Never the arguments or the result.** A name outside the catalogue is recorded as `unknown`. Spans are gated on `isObservabilityEnabled`; the counters and refusal log are not.
- **Cold starts** (JEF-357): `coldStart.ts` sets `faas.coldstart` and `app.process_uptime_ms` on a process's first real request, skipping `/health`. The process runs with `--enable-source-maps`.
- **Mobile client identity** (JEF-376): `clientIdentity.ts` records the mobile app's User-Agent on the HTTP server span as `app.client.name` (`trakwyn-mobile`), `app.client.version`, `device.model.name`, `os.name` and `os.version`, leaving out empty parts. Browsers, the CLI and the extension get none. It and the cold-start flag share the http instrumentation's one `startIncomingSpanHook` (`incomingSpanAttributes.ts`). `infrastructure/device/trakwynClientUserAgent.ts` is the one parser of the format; `DeviceLabelService` uses it too.
- **Metrics:** counters live in `infrastructure/observability/metrics.ts` behind `IMetrics` and are created lazily (a meter obtained before `startObservability()` is a permanent no-op). Test them with `makeFakeMetrics()` (`__tests__/helpers/fakeMetrics.ts`). They cover:
  - cache hit/miss (`InstrumentedCache`)
  - Redis fail-open and circuit-breaker transitions for cache, rate limiter and session blocklist. Those paths degrade silently, so the counter is the only signal.
  - `trakwyn.email.sent` by `template`/`outcome`. The Brevo error keeps status and `code` only, never the body (JEF-356).
  - `trakwyn.tool.calls` by `surface`/`tool`/`outcome`, and `trakwyn.mcp.tool_refused` by `tool`/`scope` (JEF-365).
  - Postgres pool saturation (JEF-372, `infrastructure/db/poolInstrumentation.ts`): `trakwyn.db.pool.connections` (`state` = `used`/`idle`) and `trakwyn.db.pool.waiting_requests` are observable gauges read from the pool at each export, registered on its first checkout. They replace instrumentation-pg's `db.client.connection.*`, which only update on a pool event. `trakwyn.db.pool_acquire_timeouts` by `phase` (`queued`/`connecting`) counts the queries that got no connection in time, matched on pg-pool's messages (`POOL_ACQUIRE_TIMEOUT`), and logs `db.pool.acquire_timeout` at `warn` with the counts only. `POOL_MAX` is sized from these; see its comment.
- **MCP refusals:** a write tool called with a `read` token logs `mcp.tool.refused` at `warn` with `userId`, `tool` and `scope` (`SECURITY_EVENTS.MCP_TOOL_REFUSED`).
  - `trakwyn.llm.calls` and the `trakwyn.llm.duration` histogram (ms) by `provider`/`model`/`operation`/`outcome`/`error_kind`, and `trakwyn.llm.tokens` by `provider`/`direction` (JEF-113).
- **LLM calls (JEF-113):** `TracingLLMProvider` wraps the raw provider beneath `UsageTrackingLLMProvider` in `UserLLMProviderFactory.resolveForUser`. It is applied only to tracked calls (never key tests) and only when DI passes `traceLlmCalls: isObservabilityEnabled`. Each call gets one `llm.complete`/`llm.stream` client span carrying `gen_ai.provider.name` (the current name for `gen_ai.system`), `gen_ai.request.model`, `gen_ai.usage.input_tokens`/`output_tokens`, `app.llm.cache_read_tokens`/`cache_write_tokens`/`estimated`/`outcome`, and for streams `app.llm.time_to_first_token_ms`. A stream's span stays open across iteration, but its latency metric stops at `done`. A consumer that stops early is `aborted`, not `error`. A provider refusal is `ERROR` with `app.llm.error_kind` from `LlmProviderError.kind`. **No prompt, message, tool result or completion text is recorded**: an error that is not an `LlmProviderError` contributes only its class name (`error.type`), since its message could quote the response.

- **Security events (JEF-354):** `LoggingSecurityEventRepository`, a decorator over `DrizzleSecurityEventRepository`, emits one `security.<eventType>` line and increments `trakwyn.security.events`. The level is `warn` for `SUSPICIOUS_SECURITY_EVENT_TYPES`. Lines carry `userId` and `eventType` only, **never the IP or user agent**.

## Client compatibility (JEF-417)

Some clients cannot be updated on demand: a mobile build in the stores, and a Clipper installed from the Chrome Web Store. A store release cannot be rolled back, only replaced; review and slow auto-update leave old versions in use for days to weeks. So the API is not changed the way a web-only schema is.

- **The rule:** a field, mutation, argument, input field or enum value that a shipped Clipper or mobile version uses is not removed, renamed or changed incompatibly without a deprecation window. Incompatible means a removed or renamed name, a narrower input type, a new _required_ argument or input field, a changed output type, or a new value the client's code does not handle.
- **The way through:** add the new shape beside the old one, mark the old one deprecated (Pothos `deprecationReason`), keep it working, and remove it only once the versions that use it are out of use. Mobile versions are in PostHog by `$app_version`, and Clipper versions by `release` on the Clipper health dashboard (`infra/posthog/README.md`). A new optional argument is always safe.
- **The `*Mobile` mutations are the extension's contract** (`loginMobile`, `refreshTokenMobile`, `exchangeMobileOAuthCode` and the rest of `mobileAuthMutations.ts`), as well as mobile's. They return both tokens in the body because those clients have no cookie jar; do not fold them into the web mutations. Error codes a client maps to its own copy (`AI_NOT_CONFIGURED`, `RATE_LIMITED`, `UNAUTHORIZED`, …) are part of the contract too: a client that does not know a new code falls back to a generic message, so add codes, and do not repurpose one.
- **What guards it:** `apps/extension/src/__tests__/graphqlDocuments.test.ts` validates every Clipper document against this schema, using `pnpm --filter @trakwyn/api schema:print` (`http/schema/printSchema.ts`: the Pothos schema as SDL, with no database or port), and mobile's integration tier does the same against a booted API. Each fails on a removed or renamed field or argument. Neither can see a behaviour change (a different error code, a changed default), so those need the deprecation window by hand. The extension's test is part of `pnpm test`, and `apps/extension/turbo.json` lists `apps/api/src/http` as an input, so an API-only change re-runs it instead of reusing Turbo's cached result.

## AI evals (JEF-114)

Unit tests replace the model with `makeLLMProvider`, so they show the use cases handle a reply correctly, not that a prompt produces a good one. `pnpm --filter @trakwyn/api eval` (`evals/`) runs the real use cases, prompt and `parseAiJson` included, against a real provider and scores the output. It spends money and varies run to run, so it is run by hand, never by `pnpm test` or CI: vitest only matches `*.test.ts`, and nothing under `__tests__` imports the runner.

- **Covers** `ParseJobDescriptionUseCase` (12 cases: clean ads, a page with its navigation attached, German, a recruiter blurb, a prompt injection, a long posting that must be summarised) and `ComputeResumeMatchScoreUseCase` (10 pairings: strong, partial, junior for senior, adjacent field, zero overlap both ways, an injection in the resume and one in the job description). Checks are ranges and "mentions" tests, not exact strings, because a correct answer is worded differently by every model. The resume, cover letter, chat and briefing features are not covered yet.
- **Run it:** put the target in `apps/api/.env` (loaded by `--env-file-if-exists`) or export it: `EVAL_PROVIDER`, `EVAL_MODEL`, `EVAL_API_KEY`, or per provider `EVAL_API_KEY_<PROVIDER>` (`EVAL_API_KEY_ANTHROPIC`). `custom` also needs `EVAL_BASE_URL`. Flags: `--target provider[:model]` (repeat it to compare models in one table), `--case <id>[,<id>]`, `--min-pass-rate 0.8` (or `EVAL_MIN_PASS_RATE`), `--cache`, `--refresh`. Exit 0 when every target meets the pass rate, 1 when one does not, 2 for bad arguments. A full run is about 22 short requests per target.
- **The cache** (`--cache`, files in the gitignored `apps/api/.eval-cache/`) keys each reply on provider, model, messages and options, so editing a prompt or a fixture misses by itself and re-running after changing only a check costs nothing. Name the model explicitly with it: `openai:default` hides which model the default was. `--refresh` re-asks and overwrites.
- **Adding a case:** a `jobPostingCase` or `resumeMatchCase` in `evals/cases/` with its input in `evals/fixtures/` and an `idealReply`, the answer a good model would give. `cases.test.ts` feeds every `idealReply` to its own checks (so a mistyped expectation cannot fail every model for ever) and feeds the cases a model that finds nothing, or scores 2 or 98 for everything (so a check cannot pass vacuously). Fixtures are invented, never real postings or resumes.
- **Not a gate.** A score moves when a model, a prompt or a temperature does. Use it to compare a change before and after (JEF-445 reasoning off, JEF-448 cheaper models), not to block a merge.
