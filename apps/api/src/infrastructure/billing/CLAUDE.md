## Billing

The payment side of the plans in `use-cases/plans/CLAUDE.md`. A **merchant of record** is the seller, so the owner (a UK sole trader) does no VAT or sales-tax filing. Polar is the chosen provider.

- **Port and adapters:** `IBillingProvider` (`use-cases/ports/`): `createCheckoutSession`, `createPortalSession` and `parseWebhook` (signature check over the raw bytes, then a provider-neutral `BillingWebhookEvent`). `FakeBillingProvider` serves dev, CI and e2e; `PolarBillingProvider` is the real one (JEF-432). `BILLING_PROVIDER` is `fake` or `polar`; unset means fake outside production and a throw on first use in production. Registered with `asFunction`, so a missing key fails on first use. Nothing outside `infrastructure/billing/` names a provider.
- **Polar adapter (JEF-432).** Plain `fetch` pinned to `Polar-Version` (`POLAR.API_VERSION`) plus the `standardwebhooks` package, not Polar's SDK, which is versioned by import path. `buildBillingProvider` needs `POLAR_ACCESS_TOKEN`, `POLAR_WEBHOOK_SECRET`, `POLAR_SERVER` (`sandbox` or `production`, deliberately no default) and the four `POLAR_PRODUCT_*` ids, and names every missing one. The checkout carries the Trakwyn user id as `external_customer_id` and `metadata.userId`; a returning buyer is sent with `customer_id` instead, so Polar does not create a second customer. A Polar refusal is thrown as the status, the path and, for a validation error, the field names with Polar's messages (at most five). Those messages can quote what we sent, and the error is logged to Axiom and Cloud Logging outside the erasure path (JEF-348), so the buyer's email and user id are blanked from them first (`redacted` in `PolarBillingProvider.ts`).
- **Polar event mapping** (`polarWebhookEvents.ts`, tested in `polarWebhookEvents.test.ts`): `subscription.active` and `subscription.uncanceled` start a plan (the second clears a cancellation's end date); `subscription.canceled` ends it at `ends_at` or the period end; `subscription.revoked`, sent when payment retries run out, ends it at `ended_at` (a lapse is a cancellation, not a reversal). `past_due` changes nothing, so Pro continues through Polar's retries (about 21 days) before the revoke. A paid one-off order is a pass, with months from its product id; an unknown one-off product **throws**, so a payment is never silently dropped. A subscription's own orders, first or renewal, are `ignored`, so a renewal extends nothing. Only a fully refunded order is `payment_reversed`; a partial refund is ignored. Polar has no dispute event (see Known gaps below). Any event type not listed is `ignored`, and a known one whose payload cannot be read **throws** (a 500), so Polar redelivers and the log shows it.
- **The webhook's event id is Polar's `webhook-id`,** which Standard Webhooks keeps across retries; that is what `BillingEvent` dedupes on. Timestamps older than five minutes are refused by the library, so a captured delivery cannot be replayed later.
- **The client names a plan, the API picks the price.** `CreateCheckoutSessionUseCase` turns `monthly` into `founder_monthly` when `now - max(createdAt, BILLING_LIVE_FROM) < 60 days`, so the founder price cannot be asked for or stacked. An active subscriber is refused (`CONFLICT`) rather than sold a pass or a second subscription; a pass holder may subscribe (the pass is forfeited, the Plan page says so) or buy another pass (it extends).
- **The webhook is the only thing that sets a paid plan.** `POST /billing/webhook` (`http/routes/billing.routes.ts`) sits in its own plugin scope with a buffer parser, because the signature is over the bytes sent and the app-wide JSON parser would re-encode them. `HandleBillingWebhookUseCase` records the provider event id in `BillingEvent` _in the same transaction_ as the plan change: a replay finds the id and does nothing, a failure leaves neither so the provider's retry applies it once. A bad signature is 401; any other failure is 500 so the provider redelivers. Rules: subscription starts → `pro`/`subscription`/no expiry; pass → `pro`/`pass`/`max(now, current pass expiry) + 3 or 6 months`; cancellation → `planExpiresAt = end of paid period` (only for the subscription the user is on); refund or chargeback → free now (only when it reverses what the user is on). An event naming no known user is recorded and ignored, so it is not retried forever.
- **User columns** `billingCustomerId` and `billingSubscriptionId` are provider-neutral. `BillingEvent` cascades with its `User`.
- **Known gaps and rules (JEF-433 sandbox run; runbook in `infra/polar/README.md`).**
  - **Escalated disputes send no event and have no endpoint.** Only a refund Polar issues to _prevent_ a dispute arrives (as `order.refunded`, handled). An escalated one leaves the user on Pro, so the operator downgrades by hand with `plan set --plan free`.
  - **A refund does not end a Polar subscription.** The operator refunds the order in full and then revokes the subscription immediately; cancelling at period end leaves it active, blocks resubscribing and keeps renewing (renewals are ignored, so the customer would pay and stay Free).
  - **Deleting an account stops the Polar subscription before anything is lost (JEF-439, JEF-463).** Confirming a deletion sets it to cancel at period end (`scheduleCancellation`), and the purge revokes it (`revokeSubscription`, `DELETE /subscriptions/{id}`, token scope `subscriptions:write`) before the blobs and the row go; see "Account deletion and step-up" in `use-cases/auth/CLAUDE.md`. If Polar cannot be reached or refuses, confirming stops with `SERVICE_UNAVAILABLE` and changes nothing, and the purge skips that account until the next run; the provider's own error goes to the log. A 403 (already revoked) or 404 from Polar counts as done, and a 409 (pending an update) is a retry. Users without a subscription never read the billing provider, which matters because it throws when `BILLING_PROVIDER` is unset. A subscription whose `billingSubscriptionId` was already cleared (a refund without a revoke) is not found by this, so the runbook's refund rule still applies.
  - **`createCheckoutSession` does not check `PLANS_ENFORCED`; only the UI hides the buttons.** Anyone signed in can call it by hand, so a sandbox provider on production lets a user buy Pro with a test card. Test against production in one sitting and revert (runbook, "Switching an environment on, and off again").
- **Web:** checkout and the portal are on the Plan page (`/settings/plan`), shown only where `PLANS_ENFORCED` is on. The mutations are `createCheckoutSession(plan)` and `createBillingPortalSession`; both return a `url` to send the browser to.
- **Dev:** with the fake provider, "checkout" returns to the Plan page with `?fake_checkout=<product>`; to complete a purchase post a body signed with `signFakeWebhook` (`infrastructure/billing/FakeBillingProvider.ts`) to `/billing/webhook`, as `billingWebhook.integration.test.ts` does. Provider setup and launch steps are in `infra/polar/README.md`.
