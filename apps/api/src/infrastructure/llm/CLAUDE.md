# apps/api/src/infrastructure/llm - subsystem notes

Loaded when working under `apps/api/src/infrastructure/llm`. The rest of the API notes are in `apps/api/CLAUDE.md` and the layer map is in the root `CLAUDE.md`. Paths below are relative to `apps/api/src/` unless stated.

## Reasoning tokens

Hidden thinking bills at the output price and counts against `LLM.MAX_OUTPUT_TOKENS_CAP`, so it can cut a resume off. Every AI call states how much it may spend.

- **Per-call option.** `reasoning?: 'off' | 'low' | 'default'` is on `LLMCompleteOptions` and, as `LLMStreamOptions`, on `completeWithToolsStream`. Each use case passes `AI_REASONING_DEFAULTS.<FEATURE>` (`use-cases/constants.ts`), all `off`; raise one only after comparing with the JEF-114 evals. It applies to own-key users too. A new AI call site passes it.
- **Mapping is a pattern list** (`REASONING_CONTROL`, `infrastructure/config/constants.ts`), because providers do not say which models can disable thinking. Google: `generationConfig.thinkingConfig.thinkingBudget` for `gemini-2.5-flash*` (off = 0) and `gemini-2.5-pro` (off = 128, its minimum). OpenAI: `reasoning_effort` only on `api.openai.com` and for `gpt-5*` (off = `minimal`) and `o<digit>*` (off = `low`, no `minimal` there). **Every other backend, and any model matching nothing, never gets the field** (an unknown parameter can be a 400); `providerRegistry.test.ts` checks each entry. Anthropic is untouched (extended thinking is opt-in).
- **Recorded:** `LLMUsage.reasoningTokens` (Gemini `thoughtsTokenCount`, OpenAI `completion_tokens_details.reasoning_tokens`) goes to `LlmUsageEvent.reasoningTokens` (nullable; already inside `completionTokens`) and the `app.llm.reasoning_tokens` span attribute.

## Hosted AI: the platform-owned provider

Trakwyn AI: a user with no key of their own gets answers on keys the platform holds. Off unless `HOSTED_AI_ENABLED=true`; then `PlatformLLMProviderFactory.isEnabled()` is the one place that is read, and with it off every path below is skipped, so self-hosted, dev and CI are unchanged (`AI_NOT_CONFIGURED` still comes back).

- **Which key answers**, for a user who has not saved a provider order (JEF-503, `use-cases/user/CLAUDE.md`), is `User.aiSource` (`auto` default, `trakwyn`, `own`; `AI_SOURCE`), set with `setAiSource` (`SetAiSourceUseCase`, which refuses `trakwyn` while hosted AI is off). `UserLLMProviderFactory.resolveForUser` decides: `trakwyn` always uses the platform; `own` never does; `auto` uses the user's key when it resolves one and the platform otherwise, **but only when the caller named no provider** (a chat locked to a key asks for that key). `trackUsage: false` (the key test) never reaches the platform. `LimitEnforcingLLMProviderFactory` hands a `trakwyn` user straight to the inner factory, since they have no key to limit; `auto` with a key is limited exactly as before. `LLMProviderResolution.source` is `byok | platform`, and `UsageTrackingLLMProvider` records it as `LlmUsageEvent.source`.
- **Platform providers (JEF-453): Cloudflare Workers AI only.** `PlatformLLMProviderFactory` (`infrastructure/llm/`, behind the `IPlatformLLMProviderFactory` port) builds `OpenAICompatibleLLMProvider`s aimed at Cloudflare's REST route, `https://api.cloudflare.com/client/v4/accounts/<PLATFORM_CLOUDFLARE_ACCOUNT_ID>/ai/v1/chat/completions`, with `Authorization: Bearer <PLATFORM_CLOUDFLARE_API_TOKEN>` and `cf-aig-gateway-id: <PLATFORM_CLOUDFLARE_GATEWAY_ID>` (default `trakwyn`). There is no Google or OpenAI key on the platform path, and no direct provider call; users' own keys still go through `PROVIDER_REGISTRY` unchanged. It is registered with `asFunction` and reads env on each call, so a missing token or account id fails on first use (`AiNotConfiguredError`), not at boot. Models are `PLATFORM_LLM.MODELS[tier]`, a primary then a failover, chosen by tier (see "Model tiers" below). A model the caller or the user's saved key names is **not** passed on. The route is config, so it skips `IOutboundUrlPolicy`; a **user-supplied** `baseUrl` still goes through it. The gateway has logging and caching off (`infra/cloudflare/ai_gateway.tf`).
- **Failover** is `FailoverLLMProvider`: one retry on the second model (the other Workers AI model, same gateway) when the first fails with an `LlmProviderError` of kind `rate_limited` or `unavailable` (429 and 5xx), before any streamed event. Never on a 4xx, after output has started, or when the caller aborted. Each leg carries its own tracing and usage tracking, so the call that answered is the one recorded, with its own provider and model; a failed first leg records nothing. A failover logs `llm.platform.failover` at `warn`. **A leaked tool call (JEF-541)** also fails over: gpt-oss sometimes returns its reasoning and call as `content` with channel markers (`LEAKED_TOOL_CALL.MARKER`) and no `tool_calls`. `OpenAICompatibleLLMProvider` holds back streamed text that contains markers or opens with "analysis", and at `done` throws `LlmProviderError('unavailable')` when markers came with no tool call (`leakedToolCall.ts`). The leak rate on the hosted path has not been measured.
- **Dev and CI.** With `LLM_PROVIDER_MODE=fake` both legs are OpenAI-compatible providers pointed at this server's own fake completions route (`PLATFORM_LLM.FAKE_COMPLETIONS_PATH`, which `ROUTES.LLM_FAKE_COMPLETIONS` re-exports) and need no keys, so set `HOSTED_AI_ENABLED=true` to exercise Trakwyn AI in e2e.
- **Staged rollout (JEF-453).** `isEnabled()` is the global switch; `isEnabledFor(userId)` is what `UserLLMProviderFactory`, `LimitEnforcingLLMProviderFactory` and `SetAiSourceUseCase` ask. It adds `HOSTED_AI_ALLOWLIST` (comma-separated user ids) and `HOSTED_AI_ROLLOUT_PERCENT` (unset = 100, junk = 0) on top: a user is in when allowlisted or when `sha256(userId)` mod 100 is below the percent (`infrastructure/llm/hostedAiRollout.ts`). Someone outside behaves as if hosted AI were off. Stages and gates are in `infra/gcp/README.md`.
- **Reasoning on Workers AI (JEF-453, JEF-445).** The models think by default and report no separate reasoning-token count (it is inside `completion_tokens`, so `reasoningTokens` is null here and the cost estimate is still right). `REASONING_CONTROL.WORKERS_AI_MODELS` holds the request fields found by probing, since Cloudflare's docs do not name them: Gemma 4 takes `chat_template_kwargs: { enable_thinking: false }` (thinking fully off, and it ignores `reasoning_effort`); gpt-oss has no off switch, so `off` and `low` both send `reasoning_effort: 'low'`. They reach the request through `OpenAICompatibleLLMProvider`'s `reasoningFields` argument (`workersAiReasoning.ts`). Check "no `reasoning_content` in the response" for Gemma; gpt-oss always returns a little.
- **Neurons, reasoning output and gateway metadata (JEF-497).** Three additions on the platform path, none of which replaces the price-table estimate:
  - **`LlmUsageEvent.neurons`** is the `usage.neurons` Workers AI returns (nullable `double`); **`reasoningReturned`** is whether the response carried `reasoning` or `reasoning_content` text (nullable `boolean`). `OpenAICompatibleLLMProvider` reads both into `LLMUsage` (the flag only when seen, from the deltas for a stream, since its usage chunk comes last). `UsageTrackingLLMProvider.record` stores `reasoningReturned` for a **finished platform** call only, `false` meaning "no thinking text seen"; an own-key call or a stream cut off before `done` stores null. This is how "reasoning off held" is measured, because Workers AI reports no reasoning-token count.
  - **Estimate versus neurons.** `neuronsToMicros` is `WORKERS_AI_BILLING.MICRO_USD_PER_NEURON` (11, i.e. $0.011 per 1,000). A finished platform call with neurons adds `trakwyn.llm.neuron_cost_micros` (chart it beside `cost_micros`) and, when it differs from the estimate by more than `MISMATCH_TOLERANCE` (25%) **and** `MISMATCH_MIN_MICROS` (200), counts `trakwyn.llm.cost_mismatch` by `model`/`direction` and logs `llm.cost_mismatch` at `warn` (numbers only). `under` means the table is below what Cloudflare billed, so the daily breaker undercounts. The monitor and the chart are in `infra/axiom/monitors.tf`; renaming either metric means changing them in the same PR.
  - **`cf-aig-metadata`.** `IPlatformLLMProviderFactory.legs(tier, { userId, feature })` puts `{ user, feature, tier }` on every real gateway request (`gatewayMetadata.ts`). `user` is the first 16 hex characters of `sha256(userId)`: opaque to Cloudflare, but Trakwyn can recompute it to find who a gateway row belongs to. Never an email or the raw id, and no key starts `cf.` (reserved). The fake route is this server, not the gateway, and gets no header. **Unverified:** whether the gateway's analytics and spend limits can group by metadata while `collect_logs` is off (`infra/cloudflare/ai_gateway.tf`). If they cannot, per-user spend comes from `LlmUsageEvent` (`source = 'platform'`), which already has the user, cost and feature.
- **Credits (Hosted AI 4, JEF-447):** see `use-cases/plans/CLAUDE.md`.
- **Not here yet:** the settings UI (8). Guardrails are "Hosted AI spend guards" below. Infra and the runbook are `infra/cloudflare` and `infra/gcp/README.md` ("Hosted AI").

## Hosted AI spend guards

Three layers in front of the platform's keys, all in `LimitEnforcingLLMProviderFactory.guardHostedCall`, which runs after the inner resolution, **only** when `source === 'platform'` and `trackUsage !== false`, and **before** the credit charge, so a refused call costs the user no credit. Own-key calls and key tests never reach it.

- **Verified email.** A null `emailVerifiedAt` is `EmailNotVerifiedError("Verify your email to use Trakwyn AI.")` (the JEF-438 code, 403). This reads the user row, not `AssertEmailVerifiedUseCase`, so `EMAIL_VERIFICATION_REQUIRED=false` does not lift it.
- **Rate limit.** `hostedAiRateLimiter` (`RATE_LIMIT.HOSTED_AI`, 10 a minute, key `hosted-ai:user:<id>`) is an ordinary `limiter`, not `productionOnlyLimiter`: it is per user, so no suite trips it. The 11th is `RATE_LIMITED`. Like every `IRateLimiter` it fails open on a Redis error; the breaker below is what bounds spend then.
- **Daily breaker.** `IAiSpendGuard` (`HostedAiSpendGuard` over an `IAiSpendCounter`: `RedisAiSpendCounter` when `CACHE_PROVIDER=redis`, `MemoryAiSpendCounter` otherwise). The key is `hosted-ai:spend:<UTC date>` (`HOSTED_AI_SPEND`), checked before each hosted call and incremented by `costMicros` in `UsageTrackingLLMProvider.record` for `platform` calls, so the call that crosses the budget is allowed and the next is refused. **It fails closed:** an unreadable counter is `AiTemporarilyUnavailableError` (`AI_TEMPORARILY_UNAVAILABLE`, 503), unlike the rate limiter and session blocklist. A failed increment is logged and swallowed. Every refusal logs `hosted_ai.breaker_open` at `warn` (with `reason`) and counts `trakwyn.hosted_ai.breaker_open`.
- **Budget.** `HOSTED_AI.DAILY_BUDGET_MICROS` ($10), or `HOSTED_AI_DAILY_BUDGET_USD` (read on every check; junk or a negative falls back to the default).
- **Blind spots.** A model with no price (`costMicros` null) adds nothing to the counter, so the provider-side budgets (`infra/gcp/README.md`, "Hosted AI spend budgets") are the backstop. In-flight calls can overshoot the line by their own cost.
- **Monitors** are in `infra/axiom/monitors.tf`; renaming the metric or the log event means changing them in the same PR.

## Hosted AI model circuits

A health circuit per Workers AI model, in front of the spend guards above. The spend breaker refuses calls to protect the budget; a circuit refuses them because the model is down, so a user does not wait out `LLM.REQUEST_TIMEOUT_MS` on every request while it is. The word "breaker" in metrics and logs is the spend one; the health one is always "circuit".

- **Where it sits.** `HostedAiCircuits` (`infrastructure/llm/`, a `SINGLETON` because `PlatformLLMProviderFactory` builds fresh providers on every call) keeps one `CircuitBreaker` (`infrastructure/resilience/`, shared with the Redis paths) per model id, created on first use. `UserLLMProviderFactory.resolvePlatform` leaves out a leg whose circuit is open and wraps each remaining leg as `CircuitBreakingLLMProvider(track(leg))`. The circuit is outside the tracker, so a refused call writes no `LlmUsageEvent`, and inside `FailoverLLMProvider`, which sees the refusal as an ordinary `unavailable`.
- **All models open.** `resolvePlatform` throws `AiTemporarilyUnavailableError`, which `LimitEnforcingLLMProviderFactory` already skips. That happens inside the resolution, before `chargeCredits`, so the user's next listed provider answers and nothing is charged. With nothing else listed the user sees the 503 and its message. "No legs at all" is still `AiNotConfiguredError`.
- **What counts** (`classifyHostedFailure`): `unavailable` (5xx) and `unreachable`, and a raw transport failure (`TimeoutError`, `AbortError` from the idle controller, `fetch failed`, `terminated`), which the wrapper rethrows as `unreachable` since the providers let those through unmapped. **What does not:** `bad_request`, `auth`, `quota` and `rate_limited` (the model answered; `LlmProviderError` carries no `Retry-After`, so a busy model cannot be told from a sick one, and the second model already covers a 429), a call the **caller** cancelled (`signal.aborted`), and any error we do not recognise (a bug of ours must not pull a healthy model out of rotation). An `auth` failure on the platform token fails every call the same way and a circuit would not help, so it is for the Cloudflare monitors, not this.
- **Streams.** A stream holds its trial for as long as it runs (`CircuitBreaker.acquire()`), succeeds when it completes and fails on an error at any point, including after the first event. A consumer that stops early gives the slot back without a verdict.
- **Policy.** `HOSTED_AI_CIRCUIT`: three consecutive counted failures, 30 s cooldown, then **one** trial call; everyone else is refused until it settles. State is per process, so each Cloud Run instance has its own view.
- **Telemetry.** `trakwyn.hosted_ai.circuit_transitions` (`model`, `from`, `to`) and `trakwyn.hosted_ai.circuit_short_circuits` (`model`); `llm.platform.circuit` at `warn` when one opens and `info` when it closes. The monitor is `hosted_ai_circuit_open` in `infra/axiom/monitors.tf`.
- **`unreachable` now fails over.** `FailoverLLMProvider` used to move to the second model only on `rate_limited` and `unavailable`; a timeout or dropped connection threw straight through. It includes `unreachable` now, which is how the second model answers when the first one times out.
- **Not covered:** a user's own keys (a per-user circuit would need a key and an eviction), and the other third parties.

## Model tiers

- **Policy** is `AI_MODEL_TIER` (`use-cases/constants.ts`, no model ids): Free is `lite` for everything; Pro is `mid` for `coverLetter` and `resume`, `lite` otherwise. `aiModelTier(plan, feature)` (`use-cases/plans/`) reads it. The plan is `effectivePlan(user.plan, planExpiresAt, now)`, not the entitlements' plan, because an unenforced instance reports every user as Pro.
- **Tier to model** is `PLATFORM_LLM.MODELS[tier]` (JEF-453): `lite` is Gemma 4 26B (`@cf/google/gemma-4-26b-a4b-it`) with gpt-oss-120b as failover, `mid` is gpt-oss-120b with Gemma as failover. `IPlatformLLMProviderFactory.legs(tier)` builds both legs. Prices are `LLM_PRICES.workersai`, keyed by the `@cf/…` id; a new model needs one.
- **Where it is decided.** `UserLLMProviderFactory.resolvePlatform` picks `request.tier ?? aiModelTier(plan, feature)` and returns `tier` and `plan` on the `LLMProviderResolution` (absent on an own key). When `AiCreditService.charge` reports `overflow` and the resolution is not `lite`, `LimitEnforcingLLMProviderFactory` resolves again with `tier: 'lite'`.
- **Free hosted chat** is tighter: `chatLimitsFor(resolution)` (`use-cases/chat/chatLimits.ts`) gives `CHAT.HOSTED_FREE` (3 tool iterations, 12_000 history chars) when `source === 'platform'` and `plan === 'free'`, else `CHAT.MAX_TOOL_ITERATIONS` / `MAX_HISTORY_CHARS`. The stream use case resolves the provider before it trims history for that reason.
- **Telemetry:** `app.llm.tier` on the LLM span and a `tier` attribute on `trakwyn.llm.cost_micros` (`none` on an own key).
