# apps/api/src/infrastructure/observability - subsystem notes

Loaded when working under `apps/api/src/infrastructure/observability`. The rest of the API notes are in `apps/api/CLAUDE.md` and the layer map is in the root `CLAUDE.md`. Paths below are relative to `apps/api/src/` unless stated.

## Observability

- **Axiom via OTel** (`infrastructure/observability/tracing.ts`), **production only** (JEF-345): `isObservabilityEnabled` needs `NODE_ENV=production` plus `AXIOM_TOKEN`/`AXIOM_DATASET`. **One dataset per signal** (JEF-373): traces go to `AXIOM_DATASET`, logs to `AXIOM_LOGS_DATASET` and metrics to `AXIOM_METRICS_DATASET`. Leaving either of the last two unset disables that signal only. An Axiom correlation group links a trace to its log lines (`infra/axiom/README.md`), so don't merge the datasets back to get that link.
- **Release (JEF-362):** one value across all three apps, the full commit SHA the artifact was built from, or `dev` when there is none. The API reports it as the OTel resource's `service.version` (so every span, log and metric carries it) from `APP_RELEASE`, which `deploy-api` bakes into the image as a Docker build arg; it is not a Cloud Run env var, because Terraform owns those. Web sends it as PostHog's `release` from `VITE_APP_RELEASE`, set to `github.sha` by `.github/actions/vercel-deploy-production` (`vite.config.ts` falls back to `VERCEL_GIT_COMMIT_SHA` for builds on Vercel). Mobile registers it as a PostHog `release` super property, read from `extra.release`, which `app.config.ts` fills from `EAS_BUILD_GIT_COMMIT_HASH` or `APP_RELEASE`. Filter Axiom by `resource.service.version` and PostHog by `release` with the same SHA.
- **The SDK starts from a preload** (JEF-346): `node --import ./dist/instrumentation.js dist/index.js`. ESM hoists imports and only the `import-in-the-middle` loader can patch `graphql`/`pg`/`ioredis`/`undici`/`http`. Do not move the start into `index.ts`.
- **Root span:** it is renamed to `POST /graphql <op>` (`graphqlOperationSpanName.ts`, via a Mercurius `preExecution` hook) or `POST /mcp tools/call <tool>` / `POST /mcp tools/list` (`interface-adapters/mcp/mcpOperationName.ts`, from the MCP route). Both go through `operationSpanName.ts`. Only our own method and tool names reach a span name; anything else is `unknown`. `formatError` marks it `ERROR` with `error.type` for server faults only (not `NOT_FOUND` or a wrong password), and **never with a message**, since Drizzle errors embed query parameters.
- **Invalid documents (JEF-472):** a document that fails validation or parsing is a stale client (JEF-417), not a server fault. Mercurius throws one `MER_ERR_GQL_VALIDATION` error wrapping the real list, which `buildApp.ts`'s `errorFormatter` unwraps with `formatValidationFailure` before `formatError` sees it (`formatError` maps one error to one, and used to turn the wrapper into "Internal server error" for the client). Each message goes back as a `VALIDATION` error (HTTP stays 200). One `graphql.validation.failed` line is logged at `warn` with the sanitised `operationName` (shaped like a GraphQL name, or dropped), `client`/`clientVersion`, the count and the first ten messages clipped to 200 characters; `trakwyn.graphql.validation_failures` counts it by `client` (`mobile`, `extension`, `other`) and `client_version`. The version comes from the mobile User-Agent or, for the Clipper (JEF-473), from its `X-Trakwyn-Client: TrakwynClipper/<version>` header (`CLIENT_HEADER`, `trakwynClipperHeader.ts`; `fetch` cannot set `User-Agent`). Both are unauthenticated input, so a version is kept only if `plausibleVersion` accepts it (`1.3.1`, `1.3.1-beta.2`), since it becomes a metric attribute; a Clipper build that predates the header is still `extension` by its origin scheme, with no version. The header labels a count and grants nothing. The root span is named `POST /graphql validation_failed`, not after the operation, because the `preExecution` hook never runs and the name must come from a bounded set; the client's name is the `graphql.operation.name` attribute. The span is **not** `ERROR`, so `graphql_error_rate` ignores it. Messages can quote a literal written inline in the document; variables are never read.
- **Tool spans (JEF-365):** each MCP and chat tool call gets a `mcp.tool <name>` / `chat.tool <name>` span with `app.tool.name`, `app.tool.access`, `app.tool.surface`, `app.tool.outcome` (`ok`/`domain_error`/`internal_error`/`refused`/`invalid_params`), `app.tool.result_bytes` and, on MCP, `app.mcp.token_scope`. Only `internal_error` marks the span `ERROR`. **Never the arguments or the result.** A name outside the catalogue is recorded as `unknown`. Spans are gated on `isObservabilityEnabled`; the counters and refusal log are not.
- **Cold starts** (JEF-357): `coldStart.ts` sets `faas.coldstart` and `app.process_uptime_ms` on a process's first real request, skipping `/health` and `/ready`. The process runs with `--enable-source-maps`.
- **Mobile client identity** (JEF-376): `clientIdentity.ts` records the mobile app's User-Agent on the HTTP server span as `app.client.name` (`trakwyn-mobile`), `app.client.version`, `device.model.name`, `os.name` and `os.version`, leaving out empty parts. Browsers, the CLI and the extension get none. It and the cold-start flag share the http instrumentation's one `startIncomingSpanHook` (`incomingSpanAttributes.ts`). `infrastructure/device/trakwynClientUserAgent.ts` is the one parser of the format; `DeviceLabelService` uses it too.
- **Metrics:** counters live in `infrastructure/observability/metrics.ts` behind `IMetrics` and are created lazily (a meter obtained before `startObservability()` is a permanent no-op). Test them with `makeFakeMetrics()` (`__tests__/helpers/fakeMetrics.ts`). They cover:
  - cache hit/miss (`InstrumentedCache`)
  - Redis fail-open and circuit-breaker transitions for cache, rate limiter and session blocklist. Those paths degrade silently, so the counter is the only signal.
  - `trakwyn.email.sent` by `template`/`outcome`. The Brevo error keeps status and `code` only, never the body (JEF-356).
  - `trakwyn.tool.calls` by `surface`/`tool`/`outcome`, and `trakwyn.mcp.tool_refused` by `tool`/`scope` (JEF-365).
  - Postgres pool saturation (JEF-372, `infrastructure/db/poolInstrumentation.ts`): `trakwyn.db.pool.connections` (`state` = `used`/`idle`) and `trakwyn.db.pool.waiting_requests` are observable gauges read from the pool at each export, registered on its first checkout. They replace instrumentation-pg's `db.client.connection.*`, which only update on a pool event. `trakwyn.db.pool_acquire_timeouts` by `phase` (`queued`/`connecting`) counts the queries that got no connection in time, matched on pg-pool's messages (`POOL_ACQUIRE_TIMEOUT`), and logs `db.pool.acquire_timeout` at `warn` with the counts only. `POOL_MAX` is sized from these; see its comment.
- **MCP refusals:** a write tool called with a `read` token logs `mcp.tool.refused` at `warn` with `userId`, `tool` and `scope` (`SECURITY_EVENTS.MCP_TOOL_REFUSED`).
  - `trakwyn.llm.calls` and the `trakwyn.llm.duration` histogram (ms) by `provider`/`model`/`operation`/`outcome`/`error_kind`, and `trakwyn.llm.tokens` by `provider`/`direction` (JEF-113).
- **LLM cost, feature and source (JEF-444).** Every tracked call writes `costMicros`, `feature` and `source` on its `LlmUsageEvent`, own-key calls included.
  - **Callers say what the tokens are for.** `forUser`/`resolveForUser` take `{ feature, provider?, model?, trackUsage? }`, and `feature` is a required `AI_FEATURE` (`use-cases/constants.ts`). `aiFeatureTag.test.ts` reads the use-case sources and fails on a call without one. A new AI use case adds an `AI_FEATURE` entry. `parseCv` and `talkingPoints` exist beyond the ticket's list because those use cases call the factory too.
  - **Prices are code.** `LLM_PRICES` (`infrastructure/config/constants.ts`) is micro-USD per million tokens by provider then model: input, cached input, cache write, output. `estimateCostMicros` (`infrastructure/llm/`) is pure and returns a whole micro-USD or `null`. `promptTokens` already includes cache reads and writes, so the uncached share is what is left after taking them out. A key with no model is priced as its provider's default. A model with no entry is `null`, never a guess, and logs `llm.price_unknown` once per model per process. Prices are list prices: re-check them when adding a model.
  - **`source`** is `byok` for the user's own key and `platform` for Trakwyn AI (`LLM_USAGE_SOURCE`, see `infrastructure/llm/CLAUDE.md`). `trakwyn.llm.cost_micros` (`provider`/`model`/`feature`/`source`) counts priced calls only; the chart is in `infra/axiom`.
- **LLM calls (JEF-113):** `TracingLLMProvider` wraps the raw provider beneath `UsageTrackingLLMProvider` in `UserLLMProviderFactory.resolveForUser`. It is applied only to tracked calls (never key tests) and only when DI passes `traceLlmCalls: isObservabilityEnabled`. Each call gets one `llm.complete`/`llm.stream` client span carrying `gen_ai.provider.name` (the current name for `gen_ai.system`), `gen_ai.request.model`, `gen_ai.usage.input_tokens`/`output_tokens`, `app.llm.cache_read_tokens`/`cache_write_tokens`/`estimated`/`outcome`, and for streams `app.llm.time_to_first_token_ms`. A stream's span stays open across iteration, but its latency metric stops at `done`. A consumer that stops early is `aborted`, not `error`. A provider refusal is `ERROR` with `app.llm.error_kind` from `LlmProviderError.kind`. **No prompt, message, tool result or completion text is recorded**: an error that is not an `LlmProviderError` contributes only its class name (`error.type`), since its message could quote the response.
- **Logged events:** `oidc.jwks_unavailable` (as distinct from a forged token) and `cron.auth.rejected` with `reason`.
- **Security events (JEF-354):** `LoggingSecurityEventRepository`, a decorator over `DrizzleSecurityEventRepository`, emits one `security.<eventType>` line and increments `trakwyn.security.events`. The level is `warn` for `SUSPICIOUS_SECURITY_EVENT_TYPES`. Lines carry `userId` and `eventType` only, **never the IP or user agent**.
- **Failed sign-ins:** logged as `auth.login.failed`/`auth.totp.failed` (`logAuthFailure.ts`). An unknown email and a wrong password are both `invalid_credentials` with no user id, so the log can't be used to enumerate accounts.
- **Alerting** is Terraform in `infra/axiom/` (JEF-355; see its `README.md`). **Renaming a `METRICS.*` name, an `ADMIN_JOBS` entry or a log line's `event` field means updating `infra/axiom/monitors.tf` in the same PR.**

## Use-case spans

`traceUseCase` (`infrastructure/observability/tracedUseCase.ts`) wraps each use case's `execute()` in a `<ClassName>.execute` span. On error it records the exception and the `DomainError` `code` (`app.error.code`), then rethrows. **It records no arguments** (they carry passwords, tokens and chat text). `http/di/useCaseTracing.ts` maps the whole `useCases` registration at once, so a new `http/di/use-cases/*` module is traced as soon as it is spread in. Keep those modules plain `asClass(...)`; wrapping preserves `TRANSIENT`. Tracing handles value, promise and async-generator `execute` (the chat stream's span stays open across iteration). `AuthenticateRequestUseCase` is the one exemption (`UNTRACED_USE_CASES`). It is enforced by `__tests__/architecture/useCaseTracing.test.ts`, which also fails if a `*UseCase` is registered outside `http/di/use-cases/`.
