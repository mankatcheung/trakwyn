## Content quotas

Every user-creatable row has a ceiling, the same on every plan. They are abuse limits, not plan features, so they are hard constants in `CONTENT_LIMITS` / `FIELD_LENGTH_LIMITS` (`use-cases/constants.ts`) and do not go through `IEntitlementService`. A user already over a ceiling keeps their data and simply cannot add more.

- **Two enforcement shapes** (the `CONTENT_LIMITS` comment says why). Applications, documents, storage and questions keep a counter column and a conditional `UPDATE`. Everything else is a `COUNT(*)` pre-check in the use case through `assertUnderLimit` (`use-cases/shared/assertUnderLimit.ts`), which throws `QuotaExceededError` (`QUOTA_EXCEEDED`) naming the limit. It is not race-safe: two simultaneous creates can leave a resource one over, which is accepted for rows made a few times a month. Per-user counts come from the cached `findAllByUserId` lists (conversations pass the cap as `limit`); per-application counts use `countByApplicationId`.
- **Every route to a row must pass the guard.** Drafts are created by `CreateDocumentDraftUseCase` and by both AI generators, so all three call `assertDraftCapacity`, and the generators call it before the model. `ImportCvProfileUseCase` checks all three sections with `assertRoomFor` before its first write, and `ImportUserDataUseCase` leaves out notes past the cap or too long rather than failing the application. A new create path for a capped resource needs the same.
- **Push registration is an upsert,** so `assertCanRegisterDevice` lets a device that is already registered re-register at the cap; web and Expo are counted apart.
- **Text length** is `assertMaxLength` (`ValidationError`, never truncation) on `note.content` (create and update). Tags go through `assertValidTags`: the array is bounded by `TAGS_PER_APPLICATION` (the call replaces the tags, so its length is the final count) and each name by `TAG_NAME`. Bulk "add tag" goes through `UpdateApplicationUseCase`, so one full application fails the whole bulk call, which is one transaction.
- **Messages are trimmed, not refused.** `TrimmingMessageRepository` (a decorator over `DrizzleMessageRepository`, registered as `messageRepository`) deletes all but the newest `MESSAGES_PER_CONVERSATION` after each `create`, because the model only ever sees the last `CHAT.MAX_HISTORY_MESSAGES`. Every writer (stream, confirm, dismiss) is covered without calling anything.
- **Not capped, on purpose:** company briefings (one per application by design), and MCP OAuth clients. Dynamic client registration is unauthenticated, so a client belongs to no user and there is nothing to count against; the route is rate-limited per IP (`MCP_OAUTH_REGISTRATION`) instead.
- **Reaching clients:** `contentQuota` (`GetContentQuotaUseCase`) returns every limit and the caller's per-user usage. Per-application usage is already on `Application.sectionCounts` and `Application.tags`, so clients subtract.
