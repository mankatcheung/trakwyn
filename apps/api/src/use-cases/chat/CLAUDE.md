## Chat write proposals

The in-app assistant can ask for a create/update, but **never runs one**: the user confirms it first. Chat reads text other people wrote (postings, pasted notes) and runs on the login session with no token scope, so an injected instruction must not be able to write.

- **Propose, don't run.** `executeChatTool` (`use-cases/chat/chatAssembly.ts`) checks `IChatWriteTools.has(name)` before its read switch. A write goes `prepare` (validate the arguments against the catalogue schema, prove every record named is the caller's, build the card summary), is saved as a `ChatActionProposal` (`pending`, `CHAT.PROPOSAL_TTL_MS` = 15 minutes) and returns `{ status: 'proposed', proposalId, summary, note }` to the model. **Nothing below that branch can reach a write.** The observer records it as `proposed` (a fifth `ToolCallOutcome`, `recorder.proposed`), not `ok`.
- **`ChatWriteTools`** (`interface-adapters/llm/`) is the adapter behind the `IChatWriteTools` port, since `use-cases/` may not import the catalogue. It applies through the same `WRITE_TOOL_HANDLERS` MCP uses, so ownership checks, `assertFeature` and `DomainError`s are shared. Only declared properties survive validation (`validateToolArgs.ts`); a missing record and someone else's both read as `NOT_FOUND`. Summaries are `chatWriteSummary.ts`. It is registered in `http/di/resolvers.ts`, not the use-case module (`useCaseTracing.test.ts`).
- **No deletes.** `CHAT_TOOLS` excludes `destructive` tools, so `trash_application` is not offered. A new destructive tool is excluded automatically.
- **Confirm / dismiss** (`ConfirmChatActionUseCase`, `DismissChatActionUseCase`; GraphQL `confirmChatAction(id)` / `dismissChatAction(id)`, both behind the email-verification wall). The client sends an id only. Confirm claims the row with one conditional `UPDATE` (`claimPending`: pending, owner, not expired) **and applies the saved arguments in the same transaction**, so a double click applies once and a write that throws rolls the claim back with its partial writes. The proposal is then marked `failed` with the `DomainError` message (outside the transaction, so it survives); a non-domain error shows a generic message. `PLAN_REQUIRED` for `create_offer` therefore appears on the card. A confirm or dismiss of a proposal that is no longer pending is `CONFLICT`; another user's is `NOT_FOUND`.
- **The model learns the outcome** from a `system` row in `Message` ("User confirmed: …", "User dismissed: …", "… failed: …"). `historyToPromptMessages` sends it as a bracketed user turn (providers allow a system message only at the top), and `GetChatHistoryUseCase` never returns `system` rows to clients.
- **Stream and history.** The SSE stream gains `event: proposal` (`{ id, toolName, summary }`) while the loop carries on; after the reply is stored the proposals are attached to the assistant message (`messageId`, deliberately not a foreign key). `chatHistory` returns each message's `proposals` with their status, and a pending one past its expiry is reported `expired`. Clients render the cards from history, not from the event alone.
- **Retention.** `ChatActionProposal` cascades with its user and conversation (`onDeleteBehaviour.test.ts`). Its `args` hold the user's own data, so they are never logged or put on a span.
- **PostHog session and tool spans (JEF-568).** `StreamChatWithAssistantUseCase` passes `sessionKey: conversationId` when it resolves the provider, so a conversation is one PostHog AI session and each turn a trace; `executeChatTool` reports `userId` to the observer, which sends one `$ai_span` per tool call (see `infrastructure/observability/CLAUDE.md`). Tool arguments and results never go to PostHog, the same rule as the OTel spans.
