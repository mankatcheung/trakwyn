# apps/api/src/interface-adapters/mcp - subsystem notes

Loaded when working under `apps/api/src/interface-adapters/mcp`. The rest of the API notes are in `apps/api/CLAUDE.md` and the layer map is in the root `CLAUDE.md`. Paths below are relative to `apps/api/src/` unless stated.

## MCP server

`POST /mcp` (`http/routes/mcp.routes.ts`) is JSON-RPC 2.0, POST-only with no SSE or session handling. The route owns transport and auth; protocol logic lives in `interface-adapters/mcp/McpController.ts`.

- **Protocol version (JEF-468):** `initialize` answers with the client's `protocolVersion` when it is in `MCP.SUPPORTED_PROTOCOL_VERSIONS` (`2025-03-26`, `2024-11-05`), otherwise with `MCP.PROTOCOL_VERSION` (`2025-03-26`, the first with tool annotations). `2025-06-18` is not offered: it would oblige the route to validate an `MCP-Protocol-Version` header on every request.
- **Annotations (JEF-468):** every tool in `tools/list` carries `annotations`, derived in `mcp/mcpToolDefinitions.ts` and never written per tool: `readOnlyHint` is `access === 'read'`, `destructiveHint` is the catalogue's optional `destructive: true` tag (only `trash_application`), `idempotentHint` is true for `update_*`. They are hints for a client deciding whether to ask the user; the scope check in `tools/call` is still the boundary. A new tool that removes something from the user's view gets `destructive: true`.
- **Write dispatch:** every write tool is handled in `mcp/writeToolHandlers.ts`, a map typed `Record<WriteToolName, …>`, so a write tool added to the catalogue without a handler fails typecheck. Read tools stay in the controller's switch. Argument narrowing (`toStr`, `toDate`, `toAmount`, `toOneOf`) is `mcp/toolArgs.ts`; a closed domain set (round type and outcome, offer period) is declared once in the catalogue, advertised as an `enum` and checked again by the handler. Handlers pass only the caller's `userId`; the use case does the ownership check.
- **Errors:** a use-case failure with `NOT_FOUND`, `FORBIDDEN` or `PLAN_REQUIRED` is `INVALID_PARAMS` with the code in `error.data.code`; anything else is `INTERNAL_ERROR`. `create_offer` is the one gated write (`offers`); `update_offer` follows `UpdateOfferUseCase`, which is ungated so an offer recorded on Pro stays editable after a downgrade.
- **Call limits (JEF-465):** `tools/call` spends one call from `RATE_LIMIT.MCP_TOOL_CALL_READ` or `MCP_TOOL_CALL_WRITE` (by the tool's `access`; 300 and 60 per 5 minutes), per credential: `AuthenticateMcpRequestUseCase` returns a `tokenId` prefixed `api:`/`oauth:`, and the controller falls back to `user:<id>` without one. The check sits after the scope refusal (a refused call spends nothing) and before dispatch; `initialize`, `tools/list` and unknown tool names are not counted. A spent budget is JSON-RPC `RATE_LIMITED` (-32029) with `data.retryAfterSeconds` (the whole window, an upper bound) and the `rate_limited` tool outcome. The two limiters share one Redis keyspace, hence the `mcp-tool-call-<access>:` key prefix.
- **No hard deletes over MCP.** `trash_application` is the soft delete (restorable from Trash for 30 days); permanent deletes and bulk operations are not exposed.

- **Auth:** `AuthenticateMcpRequestUseCase` accepts API tokens of either scope (`read`/`full`) and rejects JWTs. GraphQL's `AuthenticateRequestUseCase` requires `full`, so a `read` token reaches MCP only. Every tool is scoped to the caller's `userId`.
- **Access tags (JEF-176):** each tool is `access: 'read' | 'write'`. `tools/list` hides write tools from `read` tokens, and `tools/call` **refuses** them (the refusal is the security boundary). The tag is stripped before it goes over the wire.
- **Catalogue:** `interface-adapters/llm/toolCatalogue.ts` (JEF-177). `use-cases/` never imports it; `ChatWithAssistantUseCase` gets `chatTools` injected. `http/di` decides exposure: `MCP_TOOLS` is the whole catalogue, and chat gets `CHAT_TOOLS` (every read plus every non-`destructive` write, which chat can only propose; see "Chat write proposals" in `use-cases/chat/CLAUDE.md`).
- **When adding a tool,** add it to `TOOL_CATALOGUE` _and_ to the dispatch of every surface that exposes it (MCP: the controller's switch for a read tool, `WRITE_TOOL_HANDLERS` for a write tool; also the README's tool table). The parity tests catch a tool that is advertised but not handled.
- **Write attribution (JEF-466):** `AuthenticateMcpRequestUseCase` returns an `actor` (`McpActor`, `use-cases/shared/mcpActor.ts`: `source: 'mcp'`, `apiTokenId`, `apiTokenName`) beside the scope. For an API token that is its id and name; for an OAuth grant it is the grant (family) id, which is what the user revokes, and the client's registered name. The route hands it to `McpController.handle`, which passes it to the three write handlers whose use cases log to the activity timeline (`update_application`, `create_note`, `create_interview_round`) as `actor`; they spread `actorPayload(actor)` into the log payload, so a write made in the app logs exactly what it did before. A new write tool whose use case appends to `IActivityLogRepository` must take `actor` the same way. The observer also gets the id as `ToolCallMeta.tokenId` and records `app.mcp.token_id` on **write** calls only, which covers the writes with no activity log (skills, education, work experience). Web's `ActivityTab` shows "via <name> (MCP)".
- **Tool-call observation (JEF-365):** `McpController.callTool` and `chatAssembly.executeChatTool` run every call through `IToolCallObserver.observe(meta, run)` (`use-cases/ports/`). The surface reports how the call ended through the recorder it is handed: `succeeded`, `failed`, `invalidParams`, `rateLimited` or `refused(userId)`. The OTel implementation is `infrastructure/observability/ToolCallObserver.ts`, registered in `http/di/infrastructure.ts` with the whole catalogue. A new dispatch path must go through `observe`; the parity tests in `McpController.test.ts` and `chatAssembly.test.ts` check every catalogue tool does.
